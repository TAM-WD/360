# Поиск владельца ссылки

Веб-приложение для одной организации Яндекс 360: публичная ссылка → UID владельца → локальный каталог сотрудников → письмо с запросом доступа. Доступ к файлу выдаёт сам владелец в Яндекс Диске.

Форма доступна сотрудникам и подрядчикам без входа. Имя и почту заявитель вводит сам; сервис не подтверждает его личность или существование аккаунта Яндекса.

- [Установка, настройка и эксплуатация](docs/deployment.md).

В `.env.example` находятся только демонстрационные настройки. Реальный `.env`, токены, почтовые пароли, базу и письма в репозиторий не добавляют.

Для проверки интерфейса можно запустить демо без API Яндекса и SMTP: варианты без Docker и с Docker приведены ниже. Для рабочей установки используйте инструкцию администратора.

Название организации задаётся переменной `ORGANIZATION_NAME` в серверном `.env`; числовой `YANDEX_ORG_ID` настраивается отдельно. Название не нужно вписывать в исходники. Если оно пустое, интерфейс использует «нашей организации».

## 1. Быстрая проверка без Docker

Нужен Python 3.12 или 3.13. В репозитории `TAM-WD/360` команды выполняются из `misc/get-access-to-file`, где находится `manage.py`.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
cp .env.example .env
python manage.py migrate
python manage.py sync_directory --if-empty
python manage.py runserver 127.0.0.1:8000
```

На Windows используйте `python` вместо `python3`, `.venv\Scripts\Activate.ps1` вместо `source`, `Copy-Item .env.example .env` вместо `cp`.

Откройте [http://127.0.0.1:8000](http://127.0.0.1:8000). В этой конфигурации SQLite хранит данные в `data/db.sqlite3`.

Во втором терминале, из той же папки, запустите отправку:

```bash
source .venv/bin/activate
python manage.py run_mail_worker
```

В демо `MAIL_TRANSPORT=file`: обработчик сохраняет письма в `data/mail/*.log`. Это MIME-письма; их можно прочитать текстовым редактором или скопировать с расширением `.eml` и открыть почтовой программой. Никакие письма внешним адресатам не отправляются.

Для одноразовой обработки готовых писем вместо постоянного процесса:

```bash
python manage.py run_mail_worker --once
```

Остановить локальный сервер и обработчик можно `Ctrl+C`. База, каталог и очередь сохранятся. После перезапуска используйте те же команды; `sync_directory --if-empty` не перезагружает уже имеющийся каталог.

## 2. Что проверить в интерфейсе

1. Нажмите **«Обычный файл»** под строкой поиска.
2. Появится владелец **Соколова Анна** и нормализованная ссылка.
3. Введите имя, например «Тестовый подрядчик», почту `contractor@example.com`, права и комментарий. Контакт для ответа можно указать отдельно.
4. Нажмите **«Отправить запрос»**.
5. Сначала появится «Заявка в очереди», после работы обработчика — **«Письмо сохранено в файл»**. Интерфейс обновляет статус автоматически до двух минут; затем можно нажать «Обновить статус».
6. Откройте письмо в `data/mail`. Получатель — `anna.sokolova@company.example`. В `Reply-To` — контакт заявителя, в тексте — аккаунт, требуемые права, ссылка и комментарий.

Указанная в демо почта аккаунта — тестовая: реальный аккаунт для этой проверки не нужен. В рабочем режиме владелец должен выдать доступ действительному аккаунту Яндекса. Сервис не проверяет существование аккаунта и не подтверждает личность заявителя.

| Тестовая ссылка | Ожидаемый результат |
| --- | --- |
| `https://disk.yandex.ru/d/demo-file` | Активный владелец, доступна заявка |
| `https://disk.yandex.ru/d/demo-new` | Морозов Алексей; используется для проверки обновления каталога |
| `https://disk.yandex.ru/d/demo-missing` | UID определён, сотрудника нет в каталоге; отправка недоступна |
| `https://disk.yandex.ru/d/demo-blocked` | Неактивная учётная запись; отправка недоступна |
| `https://disk.yandex.ru/d/demo-external` | Ресурс не найден или находится вне организации |

Эти ссылки вымышлены и предназначены для формы сервиса, а не для открытия настоящих файлов на сайте Яндекса. Другие ссылки в деморежиме не обслуживаются.

Дополнительные проверки:

- Введите ссылку на сторонний сайт или ссылку `/client/disk/…`: появится ошибка формата.
- Остановите обработчик, создайте заявку, перезапустите его: ожидающая заявка будет обработана.
- Повторная отправка того же `lookup_id` возвращает существующую заявку. Новый поиск того же ресурса и заявка для того же аккаунта в течение 24 часов блокируются.
- Для повторения ручного теста используйте другой тестовый адрес аккаунта. Предел по умолчанию — 5 попыток создания заявок в час с одного IP и 3 для одного аккаунта. Поиск ограничен 30 запросами в минуту с IP.
- Откройте форму на узком экране: поля должны располагаться в одну колонку.

## 3. Проверка локального каталога

Каталог загружается полностью, постранично. Из обычного запроса поиска сотрудник читается из БД. Отдельного запроса в Directory API перед каждым письмом нет.

```bash
python manage.py directory_status
```

После первой загрузки: 3 сотрудника, версия 1. Повторные поиски `demo-file` не изменяют версию.

Сымитируйте отсутствие сотрудника в локальном снимке:

```bash
python manage.py demo_cache_miss
python manage.py directory_status
```

В каталоге останутся 2 сотрудника. Теперь в интерфейсе нажмите **«Новый сотрудник»**. Поиск обнаружит неизвестный UID, загрузит полный каталог и восстановит запись. Повторный `directory_status` покажет 3 сотрудников и увеличение версии на 1. `demo_cache_miss` доступна только в демо.

Принудительное обновление для администратора сервера:

```bash
python manage.py sync_directory
```

Перезапуск с использованием существующего снимка:

```bash
python manage.py sync_directory --if-empty
```

Нюансы согласованной стратегии:

- Автоматического периодического обновления нет. Изменение почты, блокировка или увольнение известного сотрудника станут видны после следующего обновления либо служебной команды.
- Новый каталог заменяет старый только после успешной загрузки всех страниц. Сбой или некорректная страница сохраняют старый снимок.
- Одновременно выполняется одно обновление на организацию. Другие запросы короткое время ждут его, затем предлагают повторить поиск, если загрузка продолжается.
- Между автоматическими попытками обновления есть интервал `DIRECTORY_COOLDOWN_SECONDS` (60 секунд). Он предотвращает постоянные перезагрузки при неизвестных UID. В пределах этого интервала используется последний результат; новые сотрудники могут потребовать повторного поиска позже.
- Демокаталог и настоящий каталог изолированы, даже если указан одинаковый ID организации.

## 4. Проверка через Docker Compose

Нужны Docker Engine/Desktop и Compose v2. Это также основной вариант запуска на сервере с PostgreSQL.

```bash
cp .env.example .env
docker compose up --build -d
docker compose logs init
docker compose ps
```

Откройте [http://127.0.0.1:8000](http://127.0.0.1:8000). Контейнер `init` выполняет миграции и первоначальную загрузку каталога; его успешное завершение — нормальное состояние. `web`, `worker` и `db` должны работать.

```bash
docker compose logs -f worker
docker compose exec web python manage.py directory_status
docker compose exec web python manage.py demo_cache_miss
docker compose exec web python manage.py sync_directory
docker compose cp worker:/app/data/mail ./demo-mail
```

`docker compose stop` останавливает приложение, сохраняя данные. `docker compose up -d` запускает его снова. Данные PostgreSQL и тестовые письма находятся в именованных томах; не удаляйте тома, если хотите сохранить историю.

## 5. Подключение реального Яндекс 360

Нужны ID вашей организации и OAuth-токен администратора с правами:

- `cloud_api:disk.read` — настройки доступа ресурсов;
- `directory:read_users` — список сотрудников.

Можно выдать оба права одному токену или указать отдельные токены для Диска и каталога. Токен обычного пользователя с такими scope не заменяет административную роль.

Сгенерируйте отдельный секрет приложения:

```bash
python -c 'import secrets; print(secrets.token_urlsafe(48))'
```

В `.env` измените значения:

```dotenv
DEMO_MODE=false
DEBUG=false
DJANGO_SECRET_KEY=вставьте_сгенерированный_секрет
YANDEX_ORG_ID=ID_ВАШЕЙ_ОРГАНИЗАЦИИ
YANDEX_DISK_TOKEN=ТОКЕН_АДМИНИСТРАТОРА
YANDEX_DIRECTORY_TOKEN=
MAIL_TRANSPORT=file
```

Первую проверку реального поиска проведите с `MAIL_TRANSPORT=file`: реальные письма пока сохраняются локально. Защищайте эту папку, поскольку теперь письма содержат настоящие ссылки и адреса.

Для проверки только на своём компьютере по HTTP оставьте `COOKIE_SECURE=false` и `ALLOWED_HOSTS=localhost,127.0.0.1,[::1]`. SQLite допустим для этого пилота; серверную установку запускайте с PostgreSQL.

После изменения окружения перезапустите **оба процесса** или контейнеры, загрузите каталог:

```bash
python manage.py sync_directory
python manage.py directory_status
```

В Docker используйте:

```bash
docker compose up -d --build --force-recreate
docker compose exec web python manage.py directory_status
```

Возьмите реальную публичную ссылку на файл сотрудника своей организации. Проверьте имя владельца, затем создайте заявку и посмотрите тестовое письмо. Сверьте его адрес с корпоративной почтой фактического владельца.

Отдельно проверьте папку, ограниченную ссылку и ссылку без возможности скачивания. Для поиска владельца содержимое файла и публичные метаданные не скачиваются. Личные диски вне вашей организации и общие диски без однозначного сотрудника-владельца не входят в поддерживаемый сценарий.

## 6. Подключение SMTP

После проверки поиска настройте реквизиты вашего почтового сервера:

```dotenv
MAIL_TRANSPORT=smtp
MAIL_FROM=disk-access@your-company.ru
MESSAGE_ID_DOMAIN=your-company.ru
SMTP_HOST=smtp.your-company.ru
SMTP_PORT=587
SMTP_USER=disk-access@your-company.ru
SMTP_PASSWORD=СЕКРЕТ_SMTP
SMTP_USE_TLS=true
SMTP_USE_SSL=false
```

Для сервера с TLS с момента соединения на порту 465 используйте `SMTP_USE_TLS=false`, `SMTP_USE_SSL=true`. Выбирайте настройки, поддерживаемые вашим сервером. Отправитель должен быть разрешён SMTP-сервером; при необходимости используйте пароль приложения.

Перезапустите веб-приложение и обработчик. Проверьте отправку на ресурсе согласившегося на тест коллеги. Во время переключения транспорта завершите тестовую очередь: все ещё ожидающие заявки текущего режима будут обработаны с новыми настройками транспорта.

Успешный статус — **«Письмо принято SMTP-сервером»**. Он не означает прочтение письма, доставку в ящик или выдачу доступа. Временные ошибки повторяются с увеличением интервала; по умолчанию максимум 5 попыток. Постоянные SMTP-ошибки завершают заявку с ошибкой.

После устранения причины ошибки администратор сервера может повторить только неудачную заявку:

```bash
python manage.py retry_mail UUID_ЗАЯВКИ
```

Команда не переотправляет заявки со статусом успешного принятия SMTP или сохранения в файл.

Очередь обеспечивает сохранность задачи и повторные попытки. При обрыве соединения после принятия письма сервером или падении обработчика в этот момент возможна повторная доставка. Один и тот же `Message-ID` сохраняется при повторах, но SMTP не гарантирует exactly-once.

## 7. Развёртывание на сервере

Полный порядок установки, настройки API и SMTP, выпуска HTTPS-сертификата, обновления и восстановления — в [инструкции администратора](docs/deployment.md).

Базовый вариант: Ubuntu 24.04 LTS, Docker Compose, PostgreSQL, Nginx и Certbot. `Caddyfile.example` — необязательный пример для администраторов, которые используют Caddy вместо Nginx; одновременно оба прокси на одних портах не запускают.

Реальные реквизиты задаются в `.env` на сервере. Не заменяйте существующий `.env` шаблоном при обновлении. Изменения окружения требуют пересоздания контейнеров; простой `restart` их не применяет. После изменения кода образы пересобираются. Порядок с резервной копией и миграциями приведён в инструкции администратора.

## 8. Тесты

```bash
python manage.py test
python manage.py makemigrations --check --dry-run
```

Обычные тесты не обращаются к Яндексу и не отправляют внешнюю почту. Один интеграционный тест поднимает временный SMTP-приёмник **только на 127.0.0.1** и проверяет настоящее SMTP-соединение и русскоязычное MIME-письмо.

Проверяются URL, получение owner, границы организации, все страницы каталога, сбои/гонки обновления, сессии, CSRF, подмена получателя, идемпотентность заявки, ограничения повторов, смена владельца, SMTP-повторы и восстановление lease после остановки обработчика.

Два теста одновременных процессов требуют PostgreSQL и пропускаются на SQLite. Для их запуска:

```bash
docker compose exec web python manage.py test
```

У пользователя тестовой БД должно быть право создавать тестовую базу; пользователь из демо Compose его имеет. Workflow [Get access to file tests](../../.github/workflows/get-access-to-file-tests.yml) расположен в корне репозитория `360` и запускает набор на PostgreSQL из папки `misc/get-access-to-file`. Результат каждого прогона проверяйте во вкладке Actions; наличие файла само по себе не означает успешного выполнения.

## 9. Эксплуатация и ограничения

- Полный каталог, UID и адрес получателя не выдаются браузеру. Карточка показывает имя владельца и исходный ресурс. Адрес получателя определяется сервером по результату поиска, привязанному к анонимной сессии.
- Заявитель вводит свои данные сам. В письме это прямо указано. Rate limit и защита повторов ограничивают случайный спам, но не подтверждают личность и не защищают от всех видов распределённого злоупотребления.
- Поддерживаются `disk.360.yandex.ru`, `disk.yandex.ru`, `disk.yandex.com`, `yadi.sk` и публичные маршруты `/d/…`, `/i/…`, `/public/?hash=…`. Пробелы по краям убираются, схема приводится к HTTPS, значимые query/fragment сохраняются. Произвольные пользовательские URL сервером не открываются.
- Для ссылки на вложенный файл владелец определяется по опубликованному корню. В письмо включается полная проверенная ссылка с вложенным путём/параметрами. Внутренний путь на Диске не вычисляется.
- Разные URL одного файла не всегда удаётся свести к одному идентификатору. Ограничение повторов по ресурсу использует нормализованный URL; ограничения по IP и аккаунту действуют независимо от варианта ссылки.
- Каталог, заявки и очередь хранятся в БД. История и содержимое писем содержат персональные данные и ссылки на ресурсы. Доступ к БД, бэкапам и тестовым письмам должен быть ограничен администраторами сервера.
- В worker-логах только ID заявки и статус. Ошибки внешних API сохраняются как безопасные коды без токенов, URL ресурсов и тел ответов.
- Удаление старых записей выполняется явно. Сначала посмотрите объём, затем примените очистку согласно вашей политике хранения:

```bash
python manage.py prune_data --days 30
python manage.py prune_data --days 30 --apply
python manage.py clearsessions
```

Ожидающие письма и каталог не удаляются. Тестовые файлы `data/mail` очищаются отдельно. Плановое обновление каталога не настроено.

### Диагностика

| Симптом | Проверка |
| --- | --- |
| Заявка постоянно в очереди | Запущен ли `run_mail_worker`; совпадают ли БД, режим и ID организации у web/worker |
| API Яндекса отклоняет запрос | Токен администратора, scope, ID организации; после изменения scope нужен соответствующий токен |
| UID есть, но отправка недоступна | Почта/активность/тип учётной записи в каталоге; выполнить `sync_directory` |
| Владелец не появился сразу после добавления | Дождаться интервала обновления или выполнить `sync_directory` |
| Ресурс не найден | Возможны как отсутствие ссылки, так и другая организация; один HTTP 404 их не различает |
| CSRF-ошибка или потеря сессии | HTTPS, `COOKIE_SECURE`, `CSRF_TRUSTED_ORIGINS`, конфигурация proxy |
| Статус `failed` | Проверить реквизиты/права отправителя SMTP и код `last_error` заявки в БД |
| HTTP 429 | Дождаться окончания окна rate limit; за proxy проверить реальный IP |

## 10. Структура и API

```text
config/                 настройки окружения и HTTP-маршруты
portal/clients.py       фиксированные API Яндекса и демо-адаптер
portal/directory.py     полный снимок каталога и межпроцессная блокировка
portal/links.py         проверка и нормализация публичных ссылок
portal/services.py      поиск владельца и создание заявок
portal/mailqueue.py     постоянная очередь, SMTP и повторные попытки
portal/models.py        каталог, результаты поиска, заявки, лимиты
portal/templates/      интерфейс и текст письма
portal/static/         CSS и JavaScript без сборки npm
portal/management/     административные команды
portal/tests/          модульные, интеграционные и конкурентные тесты
```

API использует анонимную cookie-сессию и CSRF-защиту:

- `POST /api/resource-lookups` — `resource_url`; ответ: `lookup_id`, ссылка, имя владельца, доступность заявки.
- `POST /api/access-requests` — `lookup_id`, `requester_name`, `account_email`, `contact_email`, `rights`, `comment`; сохраняет одну заявку на результат поиска. Адрес владельца в запросе не принимается.
- `GET /api/access-requests/{uuid}` — статус заявки только из создавшей её сессии.

Первое открытие `/` устанавливает сессию и CSRF-cookie. Идентификатор поиска действует 30 минут. Перед созданием заявки владелец повторно проверяется через Disk API, адрес берётся из локального каталога. Запись заявки одновременно является записью очереди: между сохранением заявки и постановкой на отправку нет отдельного ненадёжного шага.
