# Поиск владельца ссылки: установка и эксплуатация

Инструкция для администратора заказчика. Редакция: **20 ноября 2026 года**. Соответствует поставке с интерфейсом `20261106-3`.

Базовая схема: **Ubuntu 24.04 LTS → Docker Compose → PostgreSQL + Django + обработчик писем; Nginx и Certbot на хосте**. Один экземпляр приложения обслуживает одну организацию Яндекс 360. Команды предполагают отдельный сервер без других сайтов и без ранее установленного конфликтующего Docker. Для существующего сервера адаптацию выполняет его администратор.

## 1. Назначение и состав поставки

Посетитель вставляет ссылку на ресурс Яндекс Диска. Сервис запрашивает владельца через административный API, находит его в локальном каталоге организации и предлагает отправить письмо с запросом доступа. Адрес получателя выбирает сервер. Предоставление доступа выполняет владелец в Яндекс Диске; приложение не меняет права.

Вход в сервис не требуется. Имя и почту вводит сам заявитель; их достоверность и существование аккаунта Яндекса приложение не проверяет. Для получения доступа нужен аккаунт Яндекса. Указанный email не обязан заканчиваться на `@yandex.ru`.

В комплект входят:

- репозиторий GitHub — проект с `compose.yaml`, `Dockerfile`, `.env.example`, миграциями, тестами и README;
- настоящая инструкция — настройка сервера заказчика;
- при передаче отдельно — сценарии ручной приёмки.

Настроенный `.env` создаётся на сервере. Базу, пользовательские письма и секреты не включают в репозиторий. Перед использованием отдельной инструкции по ручному тестированию замените в ней адрес тестового стенда на домен заказчика.

Контейнеры:

| Сервис | Назначение | Нормальное состояние |
| --- | --- | --- |
| `db` | PostgreSQL 17, каталог, заявки, очередь, сессии и лимиты | Работает; healthy |
| `init` | Миграции и загрузка каталога, если его ещё нет | Завершён с кодом 0 |
| `web` | Веб-страница и API | Работает; healthy |
| `worker` | Обработка постоянной очереди писем | Работает |

Данные хранятся в именованных Docker-томах. Код и статика встроены в образ: для изменения кода нужна пересборка. Python и PostgreSQL отдельно на хост устанавливать не требуется.

## 2. Что подготовить

- Ubuntu 24.04 LTS, доступ к терминалу сервера от пользователя с `sudo` и постоянный публичный IPv4. Способ подключения определяет администратор инфраструктуры.
- URL репозитория GitHub и выбранная версия: существующий тег релиза или полный хеш опубликованного коммита. Для закрытого репозитория — доступ на чтение с сервера.
- Как ориентир для небольшого пилота: 2 vCPU, 4 ГБ RAM, 20 ГБ свободного диска. Это стартовая конфигурация, не подтверждённый нагрузочным тестом минимум; для большого каталога и нагрузки ресурсы подбирают по замерам.
- Домен, например `disk.example.org`, и доступ к его DNS.
- Числовой ID организации **Яндекс 360**, её отображаемое название и доступ администратора к API.
- Почтовый ящик отправителя, SMTP-реквизиты и два согласованных тестовых ресурса.
- Доступ сервера к DNS, GitHub, HTTPS/API Яндекса, реестру Docker, репозиториям Ubuntu и SMTP-провайдеру. Сборка также скачивает Python-зависимости.

Входящие соединения: HTTP/TCP 80 и HTTPS/TCP 443 — для сайта. Порт 80 нужен также для выпуска и продления сертификата. Доступ для администрирования настройте по правилам инфраструктуры; если используется SSH, разрешите его фактический порт только из согласованной сети. PostgreSQL наружу не публикуется. В Compose оставьте публикацию приложения `127.0.0.1:8000:8000`.

**Обозначения:** `OWNER/REPOSITORY`, `vX.Y.Z`, `vNEXT`, `disk.example.org`, `example.org` и значения `ЗАМЕНИТЕ_…` замените данными заказчика. Это не готовые реквизиты и не названия существующих релизов. В серверных командах каталог проекта всегда `~/apps/disk-access`; выполняйте их от одного и того же пользователя. Команды Git выполняются без `sudo`.

## 3. Доступ к Яндекс 360

1. Войдите под администратором нужной организации. Подготовьте её числовой ID; ID каталога/облака Yandex Cloud сюда не подходит.
2. Создайте OAuth-приложение на [Яндекс OAuth](https://oauth.yandex.ru/). Для используемой поставки нужны `cloud_api:disk.read` и `directory:read_users`.
3. Получите токен от имени администратора через процесс авторизации приложения. Для ручного получения официальный справочник описывает адрес `https://oauth.yandex.ru/authorize?response_type=token&client_id=CLIENT_ID` — вместо `CLIENT_ID` подставляется идентификатор OAuth-приложения.
4. Сохраните токен в `.env` на сервере. Если меняли разрешения приложения, получите новый токен.
5. Можно использовать один токен с обоими разрешениями или отдельные токены для Диска и каталога. В переменные записывают только значение токена, **без префикса `OAuth `**.

Текущая интеграция использует:

```text
GET https://cloud-api.yandex.net/v1/disk/public/resources/admin/public-settings
    public_key=<нормализованная публичная ссылка>

GET https://cloud-api.yandex.net/v1/directory/organizations/<org_id>/users
```

Наличие scope само по себе не заменяет нужные права учётной записи. Условия доступа API и политики организации проверяет администратор. Права чтения сотрудников и порядок выдачи токена описаны в [документации Яндекс 360](https://yandex.ru/dev/yandex-360/api360/ru/access). Справочник метода Диска: [проверка публичного ресурса](https://yandex.ru/dev/disk-api/doc/ru/reference/public-settings-get-admin-pkey).

## 4. Подключение и установка Docker

Откройте терминал сервера принятым у заказчика способом: прямое SSH-подключение, SSH-алиас, bastion, VPN, OS Login или консоль провайдера. Логин, ключ, порт и промежуточные узлы зависят от инфраструктуры; обязательной универсальной команды подключения здесь нет.

Убедитесь, что терминал открыт именно на нужном сервере и у пользователя есть права `sudo`. Далее все команды раздела выполняются **на сервере**. Установите Docker из официального репозитория. Блок предназначен именно для Ubuntu 24.04 (`noble`):

```bash
sudo apt update
sudo apt install -y ca-certificates curl git openssl nano
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker run --rm hello-world
sudo docker compose version
```

Ожидается успешный `hello-world` и вывод версии Compose. При уже установленном Docker сначала проверьте его совместимость; не удаляйте пакеты и работающие контейнеры вслепую. [Официальная установка Docker на Ubuntu](https://docs.docker.com/engine/install/ubuntu/).

## 5. Получение проекта из GitHub

Получите у поставщика URL репозитория и тег релиза или полный хеш коммита для установки. Команды ниже предполагают, что `compose.yaml`, `Dockerfile` и `.env.example` находятся в корне репозитория. Используйте конкретную согласованную версию, чтобы повторное развёртывание давало тот же код.

**На сервере**, для новой установки в ещё не существующий каталог:

```bash
REPOSITORY_URL='https://github.com/OWNER/REPOSITORY.git'
RELEASE_REF='vX.Y.Z'
mkdir -p ~/apps
git clone "$REPOSITORY_URL" ~/apps/disk-access
cd ~/apps/disk-access
git checkout --detach "$RELEASE_REF"
git rev-parse HEAD
```

Остановитесь при любой ошибке. После успешного переключения на выбранную версию создайте настройки:

```bash
cp -n .env.example .env
chmod 600 .env
```

Состояние `detached HEAD` ожидаемо: сервер использует зафиксированную версию. Сохраните выведенный хеш коммита в записи о развёртывании.

В примере используется HTTPS. Для закрытого репозитория администратор настраивает разрешённый способ доступа GitHub на чтение; можно заменить URL на SSH-адрес репозитория. Доступ к GitHub и вход на сервер — разные подключения, они не обязаны использовать один ключ. Токен не вставляйте в URL или команды. [Способы клонирования в документации GitHub](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository).

Если проект уже установлен, используйте раздел обновления. Не клонируйте поверх существующего каталога и не заменяйте его `.env` шаблоном.

## 6. Первичная настройка .env

Сгенерируйте **два разных значения**:

```bash
openssl rand -hex 32
openssl rand -hex 32
nano .env
```

Первое значение — для `DJANGO_SECRET_KEY`, второе — для `DB_PASSWORD`. Секрет Django должен содержать минимум 50 символов; команда выдаёт 64.

Настройте следующие значения. Сначала используем настоящие API и сохранение писем в файл, а интерфейс открываем через защищённое перенаправление на localhost по разделу 7:

```dotenv
DEMO_MODE=false
DEBUG=false
DJANGO_SECRET_KEY=ЗАМЕНИТЕ_ПЕРВЫМ_СЛУЧАЙНЫМ_ЗНАЧЕНИЕМ

ALLOWED_HOSTS=localhost,127.0.0.1,[::1]
CSRF_TRUSTED_ORIGINS=
COOKIE_SECURE=false
TRUST_PROXY_HEADERS=false
SECURE_SSL_REDIRECT=false
SECURE_HSTS_SECONDS=0

YANDEX_ORG_ID=ЗАМЕНИТЕ_ЧИСЛОВЫМ_ID
ORGANIZATION_NAME='Название организации'
YANDEX_DISK_TOKEN='ЗАМЕНИТЕ_ТОКЕНОМ'
YANDEX_DIRECTORY_TOKEN=
DIRECTORY_COOLDOWN_SECONDS=60
DIRECTORY_PAGE_SIZE=100
API_DEADLINE_SECONDS=20

MAIL_TRANSPORT=file
MAIL_FROM=disk-access@example.org
MESSAGE_ID_DOMAIN=example.org
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USER=disk-access@example.org
SMTP_PASSWORD=
SMTP_USE_TLS=false
SMTP_USE_SSL=true
SMTP_TIMEOUT=15

DB_NAME=disk_access
DB_USER=disk_access
DB_PASSWORD=ЗАМЕНИТЕ_ВТОРЫМ_СЛУЧАЙНЫМ_ЗНАЧЕНИЕМ

LOOKUP_RATE_LIMIT=30
REQUEST_RATE_LIMIT=5
REQUEST_EMAIL_RATE_LIMIT=3
REQUEST_DEDUP_SECONDS=86400
```

Почтовый адрес и домен замените существующими реквизитами заказчика. `YANDEX_DIRECTORY_TOKEN` можно оставить пустым только если токен Диска также имеет право чтения сотрудников.

Сохраните файл в nano: **Ctrl+O → Enter → Ctrl+X**. Строки с уже существующими ключами заменяйте, не создавайте дубликаты. Одинарные кавычки вокруг секретов и названия сохраняют буквальное значение, в том числе `$`; если само значение содержит одинарную кавычку, используйте корректное экранирование dotenv. `.env` не является shell-скриптом: не выполняйте `source .env`.

`ORGANIZATION_NAME` влияет на тексты сайта и сообщения, но не на авторизацию: её определяет `YANDEX_ORG_ID`. Пустое название даёт формулировку «нашей организации».

**Важно для БД:** `DB_PASSWORD` задаётся до первого запуска PostgreSQL. Изменение строки после создания тома не меняет пароль в самой БД. Ротацию выполняют отдельно, согласованно в PostgreSQL и `.env`. Для Django не меняйте секрет при обычном обновлении.

## 7. Первый запуск и закрытая проверка

**На сервере:**

```bash
cd ~/apps/disk-access
sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps -a
sudo docker compose logs --tail 100 init
```

Продолжайте только если `init` завершился с кодом 0. `web`, `worker` и `db` должны работать; `web` и `db` после запуска становятся healthy. Непустой каталог со статусом успешной синхронизации проверяется так:

```bash
sudo docker compose exec web python manage.py directory_status
curl -fsS http://127.0.0.1:8000/healthz
```

Ожидается режим `live` и ответ `{"status": "ok"}`. `/healthz` подтверждает работу HTTP-процесса, но не проверяет токен, актуальность каталога и SMTP.

Если `init` упал: прочитайте его лог, исправьте `.env`, затем повторите `sudo docker compose up -d --build`. Не переходите к следующим шагам при незагруженном каталоге.

Для закрытой проверки нужен защищённый канал от компьютера администратора до `127.0.0.1:8000` сервера. Если ваша инфраструктура разрешает SSH-перенаправление портов, используйте свой рабочий способ SSH-подключения, добавив параметры `-N -L 127.0.0.1:18080:127.0.0.1:8000 -o ExitOnForwardFailure=yes`.

Например, **на компьютере администратора**, если подключение уже настроено через SSH-алиас `disk-server`:

```bash
ssh -o ExitOnForwardFailure=yes \
  -N -L 127.0.0.1:18080:127.0.0.1:8000 \
  disk-server
```

`disk-server` — пример алиаса, его нужно заменить своим; инструкция его не создаёт. Откройте [http://127.0.0.1:18080](http://127.0.0.1:18080). Терминал туннеля остаётся занятым — это нормально. Для закрытия нажмите Ctrl+C. Если SSH-туннели недоступны, администратор организует эквивалентное защищённое перенаправление; одного терминала в консоли провайдера недостаточно для доступа браузера. Порт 8000 наружу не открывайте.

Проверьте реальный файл и папку организации, неверный URL, внешнюю ссылку и рабочую ссылку после ошибки. Создайте одну согласованную заявку: конечный статус сейчас **«Письмо сохранено в файл»**.

Для просмотра файловой копии письма **на сервере**:

```bash
cd ~/apps/disk-access
mkdir -p ~/disk-access-test-mail
chmod 700 ~/disk-access-test-mail
sudo docker compose cp worker:/app/data/mail/. ~/disk-access-test-mail/
```

Письма находятся в MIME-файлах `.log`; при необходимости копию можно переименовать в `.eml` и открыть почтовым клиентом. Это уже реальные адреса и ссылки — передавайте их только ответственным за проверку.

## 8. Настройка настоящей почты

### 8.1. Ящик и пароль

Для Яндекс 360 войдите в ящик отправителя, разрешите почтовые программы (IMAP и «Пароли приложений и OAuth-токены») и создайте пароль приложения типа «Почта». Для входа нужен полный адрес ящика. [Инструкция Яндекс Почты](https://www.yandex.ru/support/yandex-360/business/mail/ru/mail-clients/others).

Для другого SMTP-провайдера возьмите его адрес, порт, режим шифрования и допустимый адрес отправителя. Нельзя одновременно включать `SMTP_USE_TLS` и `SMTP_USE_SSL`.

### 8.2. Завершение тестовой очереди

Перед сменой транспорта прекратите тестовые заявки. На сервере:

```bash
sudo docker compose exec web python manage.py shell -c "from django.conf import settings; from portal.models import AccessRequest; print('Ожидающих заявок:', AccessRequest.objects.filter(namespace=settings.DIRECTORY_NAMESPACE, status__in=['queued','sending','retry']).count())"
```

Нужен результат `0`. При большем числе дождитесь обработки файловым транспортом либо выясните причину задержки. После переключения ожидающие заявки текущей организации будут отправляться через SMTP. Ранее завершённые `saved` автоматически не переотправляются.

```bash
sudo docker compose stop worker
nano .env
```

Измените блок почты, сохранив остальные параметры:

```dotenv
MAIL_TRANSPORT=smtp
MAIL_FROM=disk-access@example.org
MESSAGE_ID_DOMAIN=example.org
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USER=disk-access@example.org
SMTP_PASSWORD='ЗАМЕНИТЕ_ПАРОЛЕМ_ПРИЛОЖЕНИЯ'
SMTP_USE_TLS=false
SMTP_USE_SSL=true
SMTP_TIMEOUT=15
```

Для первого подключения используйте один действующий адрес в `MAIL_FROM` и `SMTP_USER`. Для сервера с STARTTLS на 587 применяются `SMTP_USE_TLS=true`, `SMTP_USE_SSL=false`; параметры подтверждает провайдер.

### 8.3. Проверка SMTP и запуск worker

```bash
sudo docker compose config --quiet
sudo docker compose up -d --no-deps --force-recreate web
sudo docker compose exec web python manage.py shell -c "from django.conf import settings; from django.core.mail import send_mail; assert settings.MAIL_TRANSPORT == 'smtp', 'SMTP не включён'; print('Принято SMTP:', send_mail('Проверка SMTP — Поиск владельца ссылки', 'Отправка через SMTP работает.', settings.DEFAULT_FROM_EMAIL, [settings.EMAIL_HOST_USER], fail_silently=False))"
```

Команда отправляет одно настоящее письмо на адрес `SMTP_USER`; для приведённой настройки это сам ящик отправителя. Если провайдер использует технический логин вместо email, заранее замените получателя в команде на свой контролируемый адрес.

Ожидается `Принято SMTP: 1`. Проверьте входящие и спам. При ошибке исправьте настройки, пересоздайте `web` и повторите проверку. Затем:

```bash
sudo docker compose up -d --no-deps --force-recreate worker
```

Создайте новую заявку на другой согласованный ресурс: старая тестовая пара «ссылка + аккаунт» может быть заблокирована от повтора на 24 часа. Успех в интерфейсе — **«Письмо принято SMTP-сервером»**. Получение и адрес ответа проверяются в почте владельца. Ответ идёт на контакт заявителя, а если он не задан — на почту аккаунта.

## 9. Домен, Nginx и HTTPS

В этом разделе **все вхождения `disk.example.org` замените доменом заказчика**. Команды рассчитаны на прямое подключение к ВМ, без CDN/дополнительного прокси.

### 9.1. DNS и сеть

Создайте A-запись поддомена, указывающую на постоянный публичный IPv4 сервера, TTL 300 или значение по умолчанию. Если есть AAAA-запись, она должна вести на корректно настроенный IPv6 этого же сайта; устаревшую запись исправьте до выпуска сертификата.

Откройте входящие TCP 80 и 443 в группе безопасности/межсетевом экране провайдера, сохранив действующий административный доступ. На компьютере с `dig` проверьте:

```bash
dig +short A disk.example.org
```

Продолжайте, когда возвращается нужный IP. Для Yandex Cloud закрепление IP описано в [документации](https://yandex.cloud/ru/docs/vpc/operations/set-static-ip), сетевой доступ — в [группах безопасности](https://yandex.cloud/ru/docs/vpc/concepts/security-groups).

### 9.2. Nginx

**На сервере:**

```bash
sudo apt update
sudo apt install -y nginx snapd
sudo systemctl enable --now nginx
sudo snap install --classic certbot
sudo ufw status
```

Только если UFW активен, добавьте разрешение для сайта. Существующие правила административного доступа сохраняются; отдельное разрешение SSH зависит от используемого порта и сети:

```bash
sudo ufw allow 'Nginx Full'
```

Создайте конфигурацию; кавычки вокруг `EOF` нужны, чтобы shell не подставил переменные Nginx:

```bash
sudo tee /etc/nginx/sites-available/disk.example.org > /dev/null <<'EOF'
server {
    listen 80;
    server_name disk.example.org;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 125s;
    }
}
EOF
sudo ln -s /etc/nginx/sites-available/disk.example.org /etc/nginx/sites-enabled/disk.example.org
sudo nginx -t
```

Если ссылка уже существует, сначала проверьте, что она указывает на нужный файл; повторно создавать её не нужно. При успешном `nginx -t`:

```bash
sudo systemctl reload nginx
sudo /snap/bin/certbot --nginx -d disk.example.org --redirect
```

Введите контактный email и примите условия выпуска сертификата. Certbot добавит HTTPS и перенаправление HTTP. До следующего шага приложение может отвечать 400 на новом домене, поскольку он ещё не внесён в `ALLOWED_HOSTS`; проверка сертификата выполняется Nginx. Если сертификат не выпущен, сначала исправьте DNS/порты и не включайте обязательный HTTPS в приложении.

Использованы [заголовки reverse proxy Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header) и [официальная схема Certbot](https://certbot.eff.org/instructions?ws=nginx&os=snap).

### 9.3. Переключение приложения на HTTPS

```bash
cd ~/apps/disk-access
nano .env
```

Замените соответствующие строки:

```dotenv
ALLOWED_HOSTS=disk.example.org,localhost,127.0.0.1,[::1]
CSRF_TRUSTED_ORIGINS=https://disk.example.org
COOKIE_SECURE=true
TRUST_PROXY_HEADERS=true
SECURE_SSL_REDIRECT=true
SECURE_HSTS_SECONDS=0
DEMO_MODE=false
DEBUG=false
```

В `ALLOWED_HOSTS` нет схемы и пути; в `CSRF_TRUSTED_ORIGINS` схема `https://` обязательна. HSTS оставлен выключенным на этапе ввода; долгий срок, includeSubDomains и preload включают отдельно после проверки доменной политики.

```bash
sudo docker compose config --quiet
sudo docker compose up -d --no-deps --force-recreate web worker
sudo docker compose ps
curl -I http://disk.example.org
curl -I https://disk.example.org
curl -fsS https://disk.example.org/healthz
sudo /snap/bin/certbot renew --dry-run
systemctl list-timers --all | grep certbot
```

Ожидаются перенаправление HTTP, ответ HTTPS 200, JSON `{"status": "ok"}` и успешная пробная проверка продления. Snap настраивает автоматическое продление; проверьте наличие таймера. Порт 80 оставьте открытым для проверки домена.

Откройте домен в браузере. Туннель больше не нужен. При включённых защищённых cookie и HTTPS-редиректе старый HTTP-адрес `127.0.0.1:18080` не является полноценным рабочим интерфейсом. Локальный `/healthz` продолжает работать, поскольку исключён из HTTPS-редиректа.

## 10. Приёмка

1. По домену открывается HTTPS без предупреждений, нет демо-кнопок и сообщения о файловой отправке.
2. Название организации соответствует `.env`; реальная ссылка файла и папки возвращает ожидаемого владельца.
3. Неверная и внешняя ссылка дают понятную ошибку; следующий рабочий поиск доступен без перезапуска.
4. Поиск в активной вкладке не остаётся в бесконечном ожидании: клиентский предел около 30 секунд.
5. На согласованном ресурсе новая заявка получает номер, SMTP принимает письмо, владелец подтверждает получение.
6. Имя, ссылка, права, аккаунт и контакт в письме верны; «Ответить» адресуется заявителю.
7. Повторная заявка для той же ссылки и аккаунта отклоняется в пределах установленного срока.
8. Форма доступна на мобильном экране; настройки сертификата и резервного копирования переданы ответственному.

Внешний ресурс может вернуть разные ошибки API. HTTP 503 не доказывает, что ресурс принадлежит другой организации. Сервис поддерживает ресурсы, для которых API возвращает одного сотрудника-владельца нужной организации; общие диски без такого владельца не считаются поддержанными автоматически.

## 11. Каталог сотрудников

```bash
cd ~/apps/disk-access
sudo docker compose exec web python manage.py directory_status
sudo docker compose exec web python manage.py sync_directory
```

Первая команда показывает состояние без запроса к Яндексу. Вторая принудительно загружает **полный** каталог. Новый снимок заменяет старый только после успешного получения всех страниц.

При поиске известного UID используется локальная запись. При неизвестном UID запускается полное обновление с учётом защитного интервала; это не отдельная загрузка одного сотрудника. Периодическое обновление автоматически не настроено. Изменение почты, блокировка или увольнение уже известного сотрудника становятся видны после обновления каталога. Ответственный администратор запускает синхронизацию после таких изменений.

При обычном запуске `init` использует `sync_directory --if-empty`: существующий каталог не обновляется. Изменение `ORGANIZATION_NAME` не требует синхронизации.

## 12. Ограничения и сроки

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `LOOKUP_RATE_LIMIT` | 30 | Поиски с IP за минутное окно |
| `REQUEST_RATE_LIMIT` | 5 | Попытки создания заявки с IP за часовое окно |
| `REQUEST_EMAIL_RATE_LIMIT` | 3 | Попытки на почту аккаунта за часовое окно |
| `REQUEST_DEDUP_SECONDS` | 86400 | Повтор той же нормализованной ссылки и аккаунта: 24 часа |
| `LOOKUP_TTL_SECONDS` | 1800 | Срок результата поиска до отправки заявки |
| `DIRECTORY_COOLDOWN_SECONDS` | 60 | Интервал автоматических попыток обновления каталога |
| `API_DEADLINE_SECONDS` | 20 | Общий срок одного вызова API, включая повторы |
| `API_TIMEOUT` | 10 | Тайм-аут сетевой неактивности |
| `MAIL_MAX_ATTEMPTS` | 5 | Максимальное число попыток отправки |
| `MAIL_RETRY_BASE_SECONDS` | 30 | Начальная задержка повторной отправки |
| `SMTP_TIMEOUT` | 15 | Тайм-аут почтового соединения |

Переменные, отсутствующие в `.env.example`, можно добавить в `.env`; поддерживаемые значения перечислены в `config/settings.py`. `API_DEADLINE_SECONDS` действует на один вызов, а не на всю многостраничную загрузку каталога. Увеличение этого значения не меняет фиксированный браузерный предел поиска в 30 секунд. Изменяя SMTP-тайм-аут, учитывайте проверку `MAIL_LEASE_SECONDS > 3 * SMTP_TIMEOUT` (по умолчанию lease — 120 секунд).

Счётчики хранятся в БД и используют фиксированные окна. Отклонённые попытки после прохождения соответствующего счётчика также могут расходовать лимит. Пользователи за одним NAT имеют общий IP. В текущей версии `Retry-After` для 429/503 фиксирован и не показывает точный остаток часового окна. Upstream 429 Яндекса отображается как 503; локальные лимиты — как 429.

Одинаковый `lookup_id` возвращает уже созданную заявку. Разные варианты URL одного ресурса не всегда объединяются в одну запись защиты повторов.

## 13. Повседневные команды

Все команды — на сервере из `~/apps/disk-access`.

```bash
sudo docker compose ps -a
sudo docker compose logs --tail 100 web
sudo docker compose logs --tail 100 worker
sudo docker compose logs --tail 100 init
sudo docker compose exec web python manage.py directory_status
```

Поток логов: `sudo docker compose logs -f web worker`; выход — Ctrl+C, контейнеры продолжают работать.

После изменения `.env`:

```bash
sudo docker compose config --quiet
sudo docker compose up -d --no-deps --force-recreate web worker
```

`restart` не перечитывает окружение. Для обновления токенов после пересоздания проверьте `sync_directory` и реальный поиск; `directory_status` сам токен не проверяет.

Остановить пользовательские запросы и отправку, сохранив БД:

```bash
sudo docker compose stop web worker
```

Запустить их вновь:

```bash
sudo docker compose up -d --no-deps web worker
```

При остановленном `web` Nginx будет отвечать 502. Для обычного перезапуска процесса без изменения конфигурации допустим `sudo docker compose restart web worker`.

Повторить только неудачную заявку после исправления причины:

```bash
sudo docker compose exec web python manage.py retry_mail UUID_ЗАЯВКИ
```

Замените `UUID_ЗАЯВКИ` полным номером. Команда работает для статуса `failed`; принятые SMTP и сохранённые в файл письма не переотправляет. Временные ошибки обработчик повторяет автоматически. SMTP допускает повторную доставку при обрыве после принятия письма; одинаковый Message-ID не гарантирует отсутствие дублей.

Очистку истории выполняют по принятому у заказчика сроку хранения. Сначала только просмотр количества:

```bash
sudo docker compose exec web python manage.py prune_data --days 30
```

После согласования удаления:

```bash
sudo docker compose exec web python manage.py prune_data --days 30 --apply
sudo docker compose exec web python manage.py clearsessions
```

`clearsessions` удаляет истёкшие сессии. Каталог и ожидающие письма команда очистки истории сохраняет. Файловые копии тестовых писем удаляют отдельно. Не используйте `docker compose down -v` и очистку Docker-томов для перезапуска: это может удалить данные.

## 14. Резервное копирование

Сохраняйте вместе: дамп PostgreSQL, `.env`, Git-репозиторий с хешем установленной версии и конфигурацию Nginx. Сертификат на новом сервере можно выпустить заново; секреты и дамп храните в защищённом месте вне этой ВМ. Простая копия папки проекта **не содержит** БД из Docker-тома.

Перед копированием выполните `git status --short` из каталога проекта. В штатном развёртывании вывод пустой; `.env` исключён через `.gitignore`. Если есть локальные изменения исходников или новые файлы, сначала сохраните и согласуйте их отдельно: Git bundle ниже содержит только коммиты и не сохраняет незакоммиченные изменения.

**На сервере, при работающей БД:**

```bash
cd ~/apps/disk-access
umask 077
BACKUP_DIR="$HOME/backups/disk-access/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$BACKUP_DIR"
sudo docker compose exec -T db sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$BACKUP_DIR/database.dump"
```

Если `pg_dump` завершился с ошибкой, копия не считается готовой. Проверьте архив, затем сохраните остальные файлы:

```bash
test -s "$BACKUP_DIR/database.dump"
sudo docker compose exec -T db pg_restore --list < "$BACKUP_DIR/database.dump" > "$BACKUP_DIR/database.contents.txt"
cp .env "$BACKUP_DIR/app.env"
git rev-parse HEAD > "$BACKUP_DIR/revision.txt"
git bundle create "$BACKUP_DIR/repository.bundle" --all HEAD
git bundle verify "$BACKUP_DIR/repository.bundle"
sudo cat /etc/nginx/sites-available/disk.example.org > "$BACKUP_DIR/nginx.conf"
printf '%s\n' "$BACKUP_DIR"
```

Используется формат дампа PostgreSQL custom; пароль не передаётся в аргументах команд. Наличие списка объектов ещё не заменяет пробное восстановление. Продолжайте только после успешного выполнения всех команд. Последняя команда показывает созданную папку — перенесите её целиком в защищённое резервное хранилище согласованным у заказчика способом: системой резервного копирования, SFTP/SCP или другим доступным каналом. Его параметры определяет администратор.

`repository.bundle` сохраняет Git-историю и текущий коммит, в том числе при `detached HEAD`. Из него можно восстановить репозиторий без доступа к GitHub; внешние зависимости для сборки по-прежнему скачиваются отдельно. URL исходного репозитория храните в эксплуатационной документации. [Документация Git bundle](https://git-scm.com/docs/git-bundle).

Если нужны файловые копии тестовых писем, сохраните их отдельно из `/app/data/mail`; для работы в SMTP основное состояние очереди уже находится в PostgreSQL. Команды выше не создают расписание резервирования. Назначьте периодичность, срок хранения и ответственного, регулярно проверяйте восстановление.

## 15. Обновление

Заранее получите тег нового релиза или полный хеш коммита и сведения о миграциях. Все команды ниже выполняются **на сервере**. Обновление включает получение кода из GitHub, пересборку образов и применение миграций.

1. Проверьте состояние репозитория и получите сведения о новых версиях:

```bash
cd ~/apps/disk-access
git status --short
git rev-parse HEAD
git fetch origin --tags
RELEASE_REF='vNEXT'
git rev-parse --verify "${RELEASE_REF}^{commit}"
```

Замените `vNEXT` существующим тегом или полным хешем нужного коммита. `git status --short` должен быть пустым. При локальных изменениях остановитесь и согласуйте их сохранение; не применяйте принудительный сброс. Запишите предыдущий хеш для возможного отката. Если получение версии завершилось ошибкой, рабочий сервис не останавливайте.

2. Согласуйте короткое окно обслуживания и остановите приём и обработку заявок:

```bash
sudo docker compose stop web worker
```

3. Выполните резервное копирование из раздела 14; БД должна оставаться работающей. Продолжайте только с проверенной копией.
4. Переключите код на выбранную версию:

```bash
git checkout --detach "$RELEASE_REF"
git rev-parse HEAD
```

Продолжайте только после успешного переключения. Если открывали новый терминал, задайте `RELEASE_REF` заново. `.env` не отслеживается Git и сохраняется. Сверьте новые параметры `.env.example` и примечания к релизу с действующим `.env`, внесите необходимые изменения вручную. Не заменяйте настройки шаблоном.

```bash
sudo docker compose config --quiet
sudo docker compose build web worker init
sudo docker compose run --rm --no-deps init
```

5. Только после успешной сборки и завершения `init` с кодом 0:

```bash
sudo docker compose up -d --no-deps --force-recreate web worker
sudo docker compose ps
curl -fsS http://127.0.0.1:8000/healthz
curl -fsS https://disk.example.org/healthz
sudo docker compose logs --tail 50 web worker
```

Проверьте поиск через браузер и, если менялась отправка, согласованную заявку. Не меняйте имя каталога Compose и имя проекта без плана переноса томов. Не запускайте `down -v`.

**Откат:** если схема БД не менялась, при остановленных `web`/`worker` выполните `git checkout --detach ХЕШ_ПРЕДЫДУЩЕЙ_ВЕРСИИ`, проверьте совместимость `.env`, пересоберите и запустите сервисы. Вместо шаблона подставьте сохранённый хеш. Если были миграции, совместимость старого кода с новой схемой должна быть подтверждена разработчиком; иначе восстанавливают согласованный комплект БД, кода и настроек. Переключение Git само по себе не откатывает БД.

## 16. Восстановление

Порядок ниже — **для новой ВМ и пустой БД**, не для перезаписи работающего сервиса. Подготовьте Docker по разделу 4 и перенесите выбранную резервную папку на новый сервер, например в `~/restore/disk-access`.

```bash
RESTORE_DIR="$HOME/restore/disk-access"
REPOSITORY_URL='https://github.com/OWNER/REPOSITORY.git'
mkdir -p ~/apps
git clone "$RESTORE_DIR/repository.bundle" ~/apps/disk-access
cd ~/apps/disk-access
git checkout --detach "$(cat "$RESTORE_DIR/revision.txt")"
git remote set-url origin "$REPOSITORY_URL"
git rev-parse HEAD
```

В `REPOSITORY_URL` укажите настоящий адрес исходного репозитория. Каталог назначения должен отсутствовать до клонирования. После успешного восстановления Git и проверки, что хеш совпадает с `revision.txt`, верните настройки:

```bash
cp "$RESTORE_DIR/app.env" .env
chmod 600 .env
nano .env
```

Проверьте домен, токены и сохранённые секреты. Для будущих обновлений восстановите доступ нового сервера к GitHub; `origin` уже указывает на исходный репозиторий. Для закрытой проверки временно используйте настройки HTTP-туннеля из раздела 6 и `MAIL_TRANSPORT=file`. **Worker пока не запускайте:** в дампе могут находиться старые ожидающие письма.

```bash
sudo docker compose up -d db
sudo docker compose ps
```

Дождитесь healthy у `db`. Затем импортируйте дамп именно в новую пустую БД:

```bash
sudo docker compose exec -T db sh -c 'exec pg_restore --exit-on-error --no-owner --no-privileges -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < "$RESTORE_DIR/database.dump"
sudo docker compose build web worker init
sudo docker compose run --rm --no-deps init
```

При ошибке восстановления или миграций не запускайте приложение. После успешного завершения:

```bash
sudo docker compose up -d --no-deps web
sudo docker compose exec web python manage.py directory_status
curl -fsS http://127.0.0.1:8000/healthz
```

Проверьте поиск через туннель. Сверьте очередь с журналами: письмо, находившееся в очереди на момент старого бэкапа, могло быть отправлено после создания копии. До запуска worker решите, какие восстановленные заявки действительно надо обрабатывать. Не начинайте автоматическую отправку только потому, что БД успешно восстановилась.

Далее настройте Nginx, DNS и новый сертификат по разделу 9; `nginx.conf` из копии используйте как справочный файл — он может ссылаться на отсутствующие старые сертификаты. Перенос трафика и прекращение работы старого worker согласуйте, чтобы одновременно не работали две копии отправителя. После проверки очереди примените SMTP по разделу 8 и запустите worker.

## 17. Диагностика

| Проблема | Что проверить |
| --- | --- |
| `init` завершился ошибкой | `docker compose logs init`; ID организации, административные права, токены, исходящий HTTPS |
| HTTP 400 после назначения домена | `ALLOWED_HOSTS`, затем пересоздание `web` |
| CSRF / потеря сессии | HTTPS, `CSRF_TRUSTED_ORIGINS`, cookie и заголовок протокола от Nginx |
| Цикл перенаправлений | `X-Forwarded-Proto $scheme` в Nginx, `TRUST_PROXY_HEADERS=true`, отсутствие лишнего CDN |
| Nginx 502 | `web` работает ли; `curl http://127.0.0.1:8000/healthz`; логи Nginx и контейнера |
| Слишком много запросов | Локальные лимиты по IP/почте и реальный IP за прокси; дождаться конца окна |
| Ошибка проверки ссылки | Сопоставить `upstream_service` и `upstream_status` в логах web; 503 приложения может соответствовать 500 или 429 Яндекса |
| Сотрудник найден со старой почтой | Принудительный `sync_directory`; известный UID сам обновление не запускает |
| Заявка долго в очереди | Worker, его БД, организация и режим должны совпадать с web |
| SMTP авторизация не проходит | Полный логин ящика, пароль приложения, разрешение почтовых программ |
| SMTP connection timeout | Исходящий порт SMTP, DNS, правильный TLS/SSL; разрешения сети провайдера |
| Письмо принято, но его нет | Входящие/спам владельца, адрес получателя, журналы почтового провайдера; это не повод сразу отправлять дубликат |
| Сертификат не выпускается/не продлевается | A/AAAA, публичные 80/443, конфигурация Nginx, логи Certbot |

Команды:

```bash
cd ~/apps/disk-access
sudo docker compose logs --tail 100 web worker
sudo nginx -t
sudo tail -n 50 /var/log/nginx/error.log
sudo /snap/bin/certbot certificates
```

Для обращения в поддержку передайте время и часовой пояс, шаги, текст ошибки, номер заявки и соответствующий фрагмент лога. `.env`, OAuth-токены и SMTP-пароль не прикладывайте. `docker compose config` без `--quiet` может раскрыть секреты — не используйте его вывод как публичный диагностический отчёт.

## 18. Передача в эксплуатацию

Зафиксируйте домен, IP, расположение проекта, версию поставки и дату запуска; назначьте владельца OAuth-приложения, ящика SMTP, каталога сотрудников, сертификата и резервных копий. Секреты передавайте через отдельное согласованное хранилище.

Согласуйте актуальные лимиты, срок хранения заявок, порядок синхронизации после кадровых изменений и канал поддержки. Анонимный доступ к форме предусмотрен архитектурой: сайт показывает имя владельца ресурса, но не публикует каталог целиком и не подтверждает личность заявителя.

Проверки запуска Docker, API и SMTP выполняются на сервере заказчика. Настоящий документ описывает воспроизводимый порядок; он не является свидетельством, что новая установка уже прошла приёмку.
