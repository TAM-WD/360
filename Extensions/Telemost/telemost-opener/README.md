# Открыватель приложений

Расширение Chromium Manifest V3, версия **2.0.0**. Перехватывает клики и навигацию верхнего уровня: ввод URL в адресной строке, выделение текста → правая кнопка → «Перейти по адресу», открытие ссылки через меню браузера. Все встроенные правила по умолчанию включены.

## Встроенные маршруты

Для обоих доменов — `telemost.yandex.ru` и `telemost.360.yandex.ru`:

| Ссылка | Адрес приложения |
| --- | --- |
| `https://<домен>/j/<идентификатор>` | `telemost://<полный HTTPS-URL>` |
| `https://<домен>/join#<непустой фрагмент>` | `telemost://ychat/<домен>/join#<фрагмент>` |
| `https://<домен>/staff/<сотрудник>` | `telemost://ychat/<домен>/staff/<сотрудник>` |

Для `/staff/` и `/join` удаляется только префикс `https://`; домен, путь, query и hash сохраняются. Например:

```text
https://telemost.yandex.ru/staff/person@example.net?selectedUid=123456789&from=auto_redirect_ms
→ telemost://ychat/telemost.yandex.ru/staff/person@example.net?selectedUid=123456789&from=auto_redirect_ms
```

В `rules.json` также включено отдельное правило `messenger-staff`: `https://messenger.360.yandex.ru/#/staff/<логин>` → `telemost://ychat/telemost.yandex.ru/staff/<логин>`. Оно сохраняет параметры внутри фрагмента после `/staff/…`, управляется собственным переключателем и не перехватывает другие разделы Мессенджера. Если ранее добавили личное правило для этих же ссылок, приоритет имеет встроенное правило из поставки.

Корень сайта, пустые `/j/` и `/staff/`, `/join` без фрагмента, другой порт, HTTP вместо HTTPS, URL с логином/паролем и похожие чужие домены встроенными правилами не перехватываются. Встроенные маршруты описаны в `rules.json`, без отдельных захардкоженных преобразований в скриптах.

## Установка и обновление

1. Сохраните [папку расширения с GitHub](https://github.com/TAM-WD/360/tree/main/Extensions/Telemost/telemost-opener) в постоянном месте на ПК. Если скачали весь репозиторий, используйте вложенную папку `Extensions/Telemost/telemost-opener`.
2. Откройте `chrome://extensions` (Edge: `edge://extensions`, Яндекс Браузер: `browser://extensions`). Включите режим разработчика и выберите **Загрузить распакованное расширение** → папку `telemost-opener`, содержащую `manifest.json`.
3. Разрешите доступ **на всех сайтах**. Для локальных HTML-файлов отдельно включите доступ к URL файлов; для инкогнито — соответствующее разрешение.
4. Обновите открытые страницы. Обработчик протокола `telemost://` должен быть зарегистрирован установленным приложением.

При обновлении замените **все** файлы в уже подключённой папке, нажмите «Обновить» на карточке расширения и перезагрузите открытые страницы. Версия на карточке должна стать **2.0.0**. Пользовательские настройки сохраняются в том же профиле при сохранении идентификатора расширения; перед переустановкой или сменой папки экспортируйте JSON. Если вручную меняли поставку, сохраните копии `config.json` и `rules.json`. Для перехода со старого общего конфига перенесите массив `rules` в `rules.json` (объект с полями `schemaVersion: 1` и `rules`), остальные настройки оставьте в `config.json`. Старый общий `config.json` пока поддерживается для совместимости и имеет приоритет над правилами из поставки, поэтому после переноса удалите из него `rules`.

## Настройки

Нажмите значок расширения: появятся независимые переключатели **Телемост: встречи**, **Телемост: чаты**, **Телемост: сотрудники** и **Мессенджер: сотрудники**. Каждый из первых трёх переключателей управляет соответствующим видом ссылок сразу на обоих доменах Телемоста. Кнопка **Все настройки и свои правила** открывает полный редактор; он также доступен через пункт «Параметры расширения».

Переключатели сохраняются сразу и применяются к кликам и фоновым переходам, в том числе на уже открытых страницах. Выключенный маршрут остаётся обычной веб-ссылкой. Пока начальные настройки ещё загружаются, обработчик кликов пропускает переход, а фоновый обработчик дожидается конфига: запрет из настроек не заменяется временным значением «включено».

## Собственные приложения

1. Вставьте исходный HTTP(S)-URL и соответствующую ассоциацию приложения.
2. Нажмите **Определить подстановку**. Расширение покажет область действия и результат.
3. В поле **Проверить на другой ссылке** замените идентификатор, query или фрагмент и проверьте итоговый адрес приложения. Предпросмотр ничего не запускает.
4. Сохраните правило. Его можно выключить, отредактировать или удалить.

Поддерживаются преобразования полного URL, URL без схемы, пути с query/hash, а также перенос идентификаторов из сегментов пути, query и фрагмента. Полный адрес может передаваться с URL-кодированием. Для query-подстановок значение копируется в исходном кодированном виде; если нужный параметр отсутствует или повторён, приложение не запускается. Поле `queryKeys` дополнительно запрещает пустое значение.

Начиная с 1.3.2 распознаётся также путь внутри фрагмента, например `#/staff/example-user`. Пара `https://messenger.360.yandex.ru/#/staff/example-user` → `telemost://ychat/telemost.yandex.ru/staff/example-user` создаёт условие `hashPathname: "/staff/{tail}"` и шаблон `telemost://ychat/telemost.yandex.ru{hashPathAndQuery}`. Ссылка с `example-user2` даст ассоциацию с `example-user2`; разделы вроде `#/chats/...` не подходят. Параметры после пути во фрагменте сохраняются при переносе всего пути.

**Уже сохранённое правило с `exactUrl` нужно пересчитать:** откройте его через **Изменить → Определить подстановку → Сохранить правило**. ID, название и состояние переключателя сохранятся. Старые точные правила не расширяют область действия автоматически. Готовый JSON для приведённой пары — `examples/messenger-staff-rule.json`: его можно вставить в поле **JSON правила** при редактировании существующего правила или добавить объект в массив `rules` файла `rules.json`. Это отдельное правило, а не полный файл для импорта конфигурации.

По одной паре невозможно однозначно восстановить произвольный алгоритм приложения. Если нет однозначной подстановки, анализатор показывает явно помеченное предложение **только для точного исходного URL**. Начиная с 1.3.4 такое новое правило нельзя сохранить, пока оно не обобщено переменными: иначе для работы пришлось бы хранить реальную ссылку в `match.exactUrl`. Уже сохранённые точные правила продолжают работать; их примеры заменяются только после обобщения и пересохранения. В разделе «Изменить шаблон вручную» можно уточнить JSON. Расширение не вычисляет подписи, одноразовые токены, шифрование или серверные перенаправления. Постоянные части ассоциации сохраняются буквально.

Автоматическое обобщение ограничено точным origin исходного URL. Для преобразования всего адреса у многоуровневого пути обычно фиксируется первый раздел, например `/room/{tail}`; для переноса отдельных идентификаторов фиксируются остальные сегменты. Проверяйте показанную область. Другой домен можно добавить явно в `match.origins`.

Приоритет — порядок правил в JSON. **Первое совпавшее правило владеет своей областью, даже если выключено.** Поэтому собственное правило не может незаметно включить отключённый встроенный маршрут. Редактор предупреждает, если пример нового правила уже занят другим правилом.

### Пример пользовательского правила

```json
{
  "id": "custom-meet",
  "name": "Рабочие встречи",
  "enabled": true,
  "userToggleAllowed": true,
  "match": {
    "origins": ["https://meet.example"],
    "pathname": "/room/{p1}",
    "queryKeys": ["pwd"]
  },
  "target": "meetingapp://join?id={path:1}&password={query:pwd}",
  "examples": [
    {
      "url": "https://meet.example/room/123?pwd=a%2Bb",
      "appUrl": "meetingapp://join?id=123&password=a%2Bb"
    }
  ]
}
```

Для ссылки `https://meet.example/room/456?pwd=c%2Fd` результат — `meetingapp://join?id=456&password=c%2Fd`.

В `pathname` поддерживаются буквальные сегменты, переменные `{p0}`, `{p1}`, … или именованные переменные вроде `{invite}` (непустая часть одного сегмента) и завершающий `{tail}` (непустой остаток пути). С версии 1.3.3 вокруг переменной разрешены буквальные префикс и суффикс: `/+{invite}`, `/file-{id}.json`. В одном сегменте допустима одна переменная; несколько переменных можно разместить в разных сегментах. Имя содержит от 1 до 40 латинских букв, цифр или `_`, начинается с буквы и учитывает регистр. Нумерация в имени `{pN}` служит обозначением; в выходном шаблоне `{path:N}` всегда берёт целый фактический сегмент по индексу N, начиная с 0, включая любые префиксы и суффиксы. Для извлечённой части используется `{capture:имя}`; имя должно быть уникальным в условии пути. Повторяющиеся старые метки `{pN}` продолжают работать с позиционными `{path:N}`, но не с обращением по имени. Query/hash в `pathname` не указываются. `hashRequired: true` требует непустой фрагмент; `queryKeys` — непустые уникальные параметры; `exactUrl` ограничивает правило одним нормализованным URL.

Необязательный `hashPathname` проверяет путь после `#` по тем же правилам, например `/staff/{p1}` или `/staff/{tail}`. Он задаётся без `#` и без параметров после `?`. Переменные `{hashPath:N}` читают сегменты этого пути с индекса 0; URL-кодирование значений сохраняется. Обычные фрагменты вроде `#room123` по-прежнему доступны через `{fragment}`.

### Для чего нужны переменные

Пример исходной ссылки:

```text
https://example.org:8443/room/123/details?id=456&mode=guest#chat
```

Для строки `{tail}` в таблице используется условие `pathname: "/room/{tail}"`.

| Переменная в `target` | Назначение | Результат для примера |
| --- | --- | --- |
| `{host}` | Передать домен и порт, без схемы и пути | `example.org:8443` |
| `{pathname}` | Передать весь путь с начальным `/`, без query и фрагмента | `/room/123/details` |
| `{pathAndQuery}` | Передать путь, query **и фрагмент**, включая `?` и `#` | `/room/123/details?id=456&mode=guest#chat` |
| `{search}` | Передать всю строку query с начальным `?` | `?id=456&mode=guest` |
| `{hash}` | Передать фрагмент с начальным `#` | `#chat` |
| `{fragment}` | Передать фрагмент без `#` | `chat` |
| `{tail}` | Передать остаток пути, совпавший с `{tail}`; без начального `/`, query и фрагмента | `123/details` |
| `{path:1}` | Взять второй **целый** сегмент пути, нумерация с 0 | `123` |
| `{query:id}` | Взять только значение параметра `id` из query | `456` |

Без query или фрагмента `{search}`, `{hash}` и `{fragment}` дают пустую строку. Если нужный query-параметр отсутствует или встречается больше одного раза, подстановка отменяется; `queryKeys: ["id"]` дополнительно требует непустого значения. `{query:id}` сохраняет исходное URL-кодирование: `id=A%2BB` даст `A%2BB`, а не `A+B`.

Дополнительные переменные:

| Переменная | Назначение |
| --- | --- |
| `{capture:invite}` | Значение именованной переменной `{invite}` из `pathname`, без фиксированного префикса и суффикса |
| `{hashCapture:invite}` | То же для переменной из `hashPathname`; имена в обычном пути и пути после `#` независимы |
| `{url}` | Полный нормализованный HTTP(S)-адрес |
| `{urlNoScheme}` | Полный адрес без `https://` или `http://` |
| `{origin}` | Схема, домен и необязательный порт |
| `{hashPathname}`, `{hashPathAndQuery}` | Путь после `#`; этот путь вместе с его параметрами |
| `{hashPath:1}` | Второй целый сегмент пути после `#`; для `#/staff/example-user` это `example-user` |
| `{hashTail}` | Остаток, совпавший с `{tail}` в `hashPathname` |
| `{capture:invite\|encode}` | Дополнительное `encodeURIComponent` от извлечённого значения; `\|encode` применим к любой переменной |

### Приглашение Telegram и части сегмента

Для пары `https://t.me/+a1b2c3` → `tg://join?invite=a1b2c3` задайте:

```json
"match": {
  "origins": ["https://t.me"],
  "pathname": "/+{invite}"
},
"target": "tg://join?invite={capture:invite}"
```

`{invite}` — выбранное вами имя. Например, для `https://t.me/+OtherCode_123` значение `{capture:invite}` будет `OtherCode_123`, а `{path:0}` останется равным `+OtherCode_123`. Отсутствующий `+`, пустой код, другой домен или лишний сегмент пути не подходят. Фиксированные части сравниваются буквально, без регулярных выражений и без URL-декодирования.

Полный готовый объект с исходной парой — `examples/telegram-invite-rule.json`. Вставьте его в **JSON правила** в редакторе. Это отдельное правило, не полный файл импорта. Можно также заново нажать **Определить подстановку** для исходной пары: анализатор распознаёт ведущий `+` и предлагает именованную переменную вроде `{code0}` с `{capture:code0}`. Произвольные префиксы и суффиксы задаются вручную. Старые сохранённые точные правила автоматически не расширяются.

Шаблон должен воспроизводить каждую исходную пару в `examples`. Исполнение JavaScript, произвольных регулярных выражений и HTTP-кода в правилах не предусмотрено. Встроенные браузерные, файловые и исполняемые схемы вроде `javascript:`, `file:` и `shell:` отклоняются.

## JSON и развёртывание в организации

В поставке настройки и правила разделены:

| Файл | Содержимое | Где хранится |
| --- | --- | --- |
| `config.json` | `schemaVersion`, общие флаги организации, необязательная карта `enabled` для начальных состояний переключателей | Папка расширения |
| `rules.json` | `schemaVersion` и массив `rules` с правилами поставки, их условиями, шаблонами и примерами | Папка расширения |
| `user-rules.json` | `schemaVersion` и массив `rules` только с пользовательскими правилами | Отдельный автоматически записываемый файл OPFS в профиле браузера |

Минимальный `config.json`:

```json
{
  "schemaVersion": 1,
  "allowUserChanges": true,
  "allowCustomRules": true
}
```

Формат обоих файлов правил: `{"schemaVersion": 1, "rules": [...]}`. Для пользовательских правил ID начинается с `custom-`. Пустой пример — `examples/user-rules.json`.

Файл `user-rules.json` создаётся при первом запуске и записывается при добавлении, изменении, отключении или удалении личного правила. Это файл в [закрытой файловой системе браузера OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system), а не файл рядом с `manifest.json`: расширение не перезаписывает собственную поставку. Для обычной копии на диске используйте **Скачать свои правила**. Скачанная копия не связана с рабочим файлом и автоматически не обновляется. Очистка данных/профиля или удаление расширения может удалить рабочий файл; для переноса используйте экспорт.

При обновлении старые пользовательские правила из `userSettings.rules` автоматически переносятся в файл. Старое поле удаляется только после успешной записи. Переключатели остаются в `chrome.storage.local`; там же хранится производный кэш `effectiveConfig` для обработчиков страниц. Источник пользовательских правил — файл, а не этот кэш. Пропавший или повреждённый ранее созданный файл не заменяется пустым автоматически: перехват отключается с ошибкой. Его можно восстановить импортом или явно сбросить настройки, если организация разрешает изменения.

При сохранении новых и редактируемых пользовательских правил значения переменных в примерах заменяются тестовыми. Числа становятся `123456`, `123457`, …; текст, логины и коды — `a1b2c3`, `a1b2c4`, … . Одинаковые значения получают одинаковую замену, разные — разные. Ассоциация примера строится заново из неизменённого шаблона; реальная подстановка при переходе продолжает использовать открываемую ссылку. Это касается переменных пути, пути после `#`, query и фрагментов. URL-кодирование обрабатывается шаблоном как раньше. Сохраняются домены, постоянные части условий и `target`: они определяют поведение правила. При импорте пользовательских правил применяется та же замена. Сами введённые примеры используются для проверки до сохранения и очищаются из редактора после него. Старые правила автоматически не переписываются; пересохраните обобщённое правило, чтобы заменить его прежние примеры.

В настройках есть три независимых кнопки скачивания: **Скачать настройки** (`config.json`), **Скачать правила поставки** (`rules.json`) и **Скачать свои правила** (`user-rules.json`). Экспорт настроек включает текущие состояния встроенных переключателей в `enabled`.

Импорт `config.json` меняет только разрешённые встроенные переключатели и сохраняет личные правила. Импорт `user-rules.json` заменяет только личные правила и сохраняет встроенные переключатели. Для изменения правил поставки замените `rules.json` в папке расширения и перезагрузите его; импорт не может подменить административные правила или флаги. Старый объединённый JSON поддерживается при импорте: разрешённые переключатели и личные правила извлекаются из него отдельно. Импорт проверяется целиком до записи. **Вернуть настройки из поставки** очищает личный файл и сбрасывает встроенные переключатели.

Основные поля конфигурации:

| Поле | По умолчанию | Назначение |
| --- | --- | --- |
| `schemaVersion` | `1` | Версия формата |
| `allowUserChanges` | `true` | Разрешает пользователю менять настройки; `false` блокирует все изменения и игнорирует старые пользовательские переопределения |
| `allowCustomRules` | `true` | Разрешает добавление, изменение и использование личных правил; при `false` ранее сохранённые личные правила не применяются |
| `rules.json → rules[].enabled` | `true` у встроенных | Значение переключателя по умолчанию; при блокировке используется именно оно |
| `rules.json → rules[].userToggleAllowed` | `true` | Разрешает менять отдельный переключатель при общем `allowUserChanges: true` |

Чтобы оставить включёнными все встроенные маршруты и запретить изменения, установите в `config.json`:

```json
"allowUserChanges": false
```

Чтобы заблокировать только встречи, задайте в `rules.json` для `telemost-j` значение `"userToggleAllowed": false`; для остальных правил оставьте `true`. Полный готовый пример общей блокировки: `examples/config-locked.json`.

### Управляемая установка

Поддерживается `chrome.storage.managed` со схемой `managed-schema.json`. Организация может задать следующие ключи политик **именно этого расширения**:

- `ConfigJSON`: настройки `config.json` как JSON-строка; старый объединённый конфиг также поддерживается.
- `RulesJSON`: файл `rules.json` как JSON-строка; перекрывает правила поставки и правила из старого `ConfigJSON`.
- `AllowUserChanges`: булево значение, перекрывает одноимённый по смыслу флаг конфига.
- `AllowCustomRules`: булево значение, перекрывает флаг личных правил.

Пример содержимого управляемой политики — `examples/managed-policy.json`. Размещение этой полезной нагрузки в GPO/MDM зависит от браузера, ОС и постоянного ID установленного расширения. Сам файл рядом с `manifest.json` не активирует политику ОС. Для массовой установки нужен управляемый канал распространения расширения со стабильным ID; установка из распакованной папки сама по себе не является механизмом организационного контроля.

Приоритет: `config.json` + `rules.json` → `ConfigJSON` + `RulesJSON` → отдельные управляемые флаги → только разрешённые пользовательские изменения. Политики перепроверяются при каждой записи. При ошибке управляемого конфига перехват отключается, в настройках отображается ошибка; включённые значения по умолчанию не применяются в обход повреждённой политики.

## Вкладки и ограничения

- Обычный клик, Ctrl/Cmd/Shift+клик, средняя кнопка и Enter на настоящих HTML/SVG-ссылках перехватываются обработчиком страницы. `href` не изменяется: копирование отдаёт исходную ссылку. Поддерживаются динамические ссылки, открытый Shadow DOM и доступные iframe.
- Фоновый обработчик действует на верхнюю навигацию вкладки; самостоятельный переход внутри iframe не переключает всю вкладку.
- При фоновом переходе на `/staff/` на обоих доменах прежний адрес **не восстанавливается**: он может автоматически перенаправлять обратно на `/staff/`. В существующей вкладке остаётся служебная страница с кнопкой закрытия, запрос приложению отправляется один раз. Это устраняет цикл перезагрузок и повторных запусков из версии 1.3.0. Обычный перехваченный клик по ссылке сохраняет исходную страницу, как и раньше.
- Та же защита от цикла применяется к собственным правилам, результат которых — `telemost://ychat/<домен Телемоста>/staff/...`, в том числе к ссылкам Мессенджера с `#/staff/...`.
- Для остальных фоновых переходов в существующей вкладке расширение возвращает прежний адрес. Иногда страница перезагружается; сохранение состояния формы не гарантируется.
- Новая пустая вкладка закрывается после передачи запроса через другую загруженную вкладку того же окна. Если такой вкладки нет, либо вкладка закреплена, остаётся служебная страница с кнопкой закрытия, чтобы не уничтожить ожидающее подтверждение приложения.
- Вкладка, с которой пользователь уже ушёл на другой сайт, не закрывается.
- `webNavigation` не отменяет запрос синхронно: вкладка может мелькнуть, HTTPS-запрос может успеть начаться. Цепочки серверных редиректов через промежуточные сервисы не гарантируются.
- На служебных страницах и закрытом Shadow DOM обработчик кликов ограничен возможностями Chromium. Исходящая верхняя HTTP(S)-навигация может обрабатываться фоновым процессом.
- Диалог подтверждения внешнего протокола остаётся под управлением браузера. Расширение не регистрирует приложения в ОС и не отменяет этот диалог. После отмены или при отсутствии приложения автоматического перехода к веб-версии нет.

Данные не передаются на внешний сервер. Разрешения `webNavigation`, `tabs`, `storage` нужны для переходов, управления вкладками и настроек. Текущие адреса вкладок и незавершённые передачи хранятся временно в `storage.session`; переключатели и производный кэш — в `storage.local`, личные правила с примерами — в файле `user-rules.json` в OPFS. Cookies и API истории не используются. Экспорт содержит сохранённые примеры. В новых и пересохранённых пользовательских правилах они тестовые; старые примеры и постоянные части правил могут содержать исходные данные.

## Проверки

Без дополнительных библиотек, Node.js 18+:

```sh
node --test tests/content.test.cjs tests/config.test.cjs tests/managed.test.cjs tests/segments.test.cjs tests/privacy.test.cjs
```

Для браузерных тестов установите Playwright и Chromium:

```sh
npm install --no-save playwright
npx playwright install chromium --no-shell
node tests/browser.cjs
node tests/navigation.cjs
node tests/redirect-loop.cjs
node tests/hash-rules.cjs
node tests/invite-rules.cjs
node tests/settings.cjs
node tests/popup-privacy.cjs
node tests/files.cjs
```

Необязательная переменная `CHROMIUM_PATH` задаёт исполняемый файл Chromium. Тесты создают отдельные профили и временные копии расширения, подменяют конечный системный вызов записью аргумента и удаляют временные файлы. Личный профиль не используется. `BASELINE=1 node tests/navigation.cjs` проверяет контрольный вариант без закрытия новой вкладки. Настройки на веб-странице загружаются асинхронно; тест кликов ожидает их готовность.

Ввод адреса проверяется через CDP `Page.navigate` с типом `typed`, создание вкладки — через настоящий `window.open()`. Сам пункт системного контекстного меню не автоматизируется; проверяется создаваемая им навигация. Корпоративные ключи проверяются на эмуляции `storage.managed`; блокировки из поставки дополнительно проверяются в настоящем браузере. Установка через конкретную GPO/MDM в тест не входит.

На macOS доступен дополнительный системный тест `node tests/native-macos.cjs`. Он создаёт временное приложение и уникальную тестовую схему, использует отдельный профиль, затем удаляет приложение и регистрацию. Сам протокол `telemost://` не меняется. Проверяется реальное получение URL тестовым приложением; запуск самого Телемоста и подтверждение его диалога нужно проверить на целевом ПК. Браузер и ОС могут нормализовать адрес после передачи (например, пустой порт во вложенном `https:`); тест строки шаблона проверяет исходный формат отдельно.

Тест `redirect-loop.cjs` проверяет автоматический переход со страницы, которая повторяет редирект при каждой загрузке: JavaScript `replace`/`assign`, meta refresh, немедленный и отложенный переход, оба домена, наличие и отсутствие `from=auto_redirect_ms`. Проверяются один вызов приложения, отсутствие повторной загрузки исходной страницы и возможность снова открыть ту же ссылку вручную. В контрольном запуске версии 1.3.0 такой сценарий дал шесть вызовов за две секунды. Перезагрузка уже использованной служебной страницы сама приложение не запускает.

Тест `hash-rules.cjs` воспроизводит сохранённое правило с `exactUrl`, пересчитывает его через редактор и проверяет другой логин, клики, ввод адреса, изменение фрагмента, JSON, перезапуск браузера и отключение правила. Отдельно проверяется отсутствие цикла для автоматического перехода Мессенджер → Телемост staff.

Тест `invite-rules.cjs` проверяет автоматическое определение приглашения с `+`, сохранение ручного правила с `{invite}`, справочник переменных, клики и ввод другого кода, закрытие новой вкладки, экспорт/импорт, перезапуск и отключение. Реальные приглашения и приложение Telegram не открываются. Тест `segments.test.cjs` проверяет именованные переменные с префиксами и суффиксами, совместимость позиционных переменных и все девять примеров справочника.

Для версии 2.0.0 пройдены **195** проверок логики, политик, файлового хранения и замены примеров, **32** сценария кликов, **34** сценария навигации, **12** проверок остановки цикла, **14** проверок настроек, **10** проверок личных hash-правил, **10** проверок приглашений, **4** проверки попапа и **6** проверок раздельных файлов — всего **317**. Браузер: Chrome for Testing **151.0.7922.34**, macOS. Системные вызовы приложений в браузерных тестах подменены; реальный запуск приложений для этого обновления не выполнялся.

`files.cjs` обновляет профиль со старым форматом хранения, проверяет реальный `user-rules.json` через OPFS, все три скачиваемых файла, независимый импорт настроек/правил, запись переключателей, удаление, перезапуск и восстановление повреждённого файла. На эмуляции дополнительно проверены ошибка записи, сохранение старой копии при неудачной миграции и запрет обхода организационных политик.

Тест личных hash-правил использует конфиг без встроенного `messenger-staff`, чтобы проверять именно пользовательское правило. Во входящий в поставку `rules.json` встроенное правило Мессенджера включено. Ручные ссылки — в `test-page.html`, номера встреч вымышлены.
