# Аудит чатов Яндекс Мессенджера

Инструмент для аудита групповых чатов и каналов в организации Яндекс 360: кто в каких чатах состоит, когда и кем был добавлен, какие боты имеют доступ к переписке.

Собирает данные из аудит-лога организации, дополняет их директорией сотрудников и, при необходимости, ручной выгрузкой. Хранит историю, чтобы отвечать на вопрос «кто был в этом чате N месяцев назад», и показывает изменения между запусками.

## Зачем это нужно

Штатных средств получить состав всех чатов организации нет. Bot API возвращает только те чаты, куда бота добавили вручную — а добавить его во все чаты программно невозможно, это ограничение платформы by design. Панель управления показывает чаты, но не даёт выгрузки.

Аудит-лог организации остаётся единственным источником, который покрывает активные чаты за определённый период. Инструмент восстанавливает состояние чатов по потоку событий и складывает события в собственную базу, чтобы не терять историю за пределами срока хранения аудит-лога (полгода).

## Что попадает в отчёт

| Данные                              | Источник                     | Полнота                         |
|-------------------------------------|------------------------------|---------------------------------|
| Название и описание чата            | аудит-лог                    | полная в пределах истории       |
| Тип чата (групповой, канал, личный) | аудит-лог                    | полная                          |
| Кто создал чат и когда              | аудит-лог                    | полная                          |
| Состав участников, роли             | аудит-лог                    | полная                          |
| Дата добавления участника           | аудит-лог                    | точная, если добавляли поимённо |
| Кто добавил участника               | аудит-лог                    | точная, если добавляли поимённо |
| Логин, ФИО, должность               | директория сотрудников       | нет для внешних участников      |
| Боты в чатах                        | флаг `is_robot` в аудит-логе | см. ограничения                 |

## Чего в отчёте принципиально не будет

**Дат добавления по каждому человеку, если его добавили вместе с группой или подразделением.** Аудит-лог создаёт одно событие на всю группу, персональных событий нет. Такие участники помечаются как приблизительные (`confidence = low`), а датой считается момент привязки группы к чату.

**Истории старше срока хранения аудит-лога.** Если чат создан год назад и с тех пор в нём не было событий, о нём не будет известно ничего. Частично это лечится ручной выгрузкой из панели управления.

**ФИО и должностей для участников из других организаций.** Их нет в директории сотрудников.

**Логинов и имён мессенджер-ботов.** Директория сотрудников таких ботов не возвращает вообще. Известен только числовой номер и флаг «это бот». Логин и имя бота можно узнать только из ручной выгрузки — инструмент связывает данные, если это однозначно возможно.

## Требования

- Python 3.11 или новее
- Тариф Яндекс 360 с поддержкой аудит-логов
- OAuth-приложение с правами:

| Право                          | Зачем                        |
|--------------------------------|------------------------------|
| `ya360_security:read_auditlog` | чтение событий — обязательно |
| `directory:read_users`         | логины, ФИО, должности       |
| `directory:read_groups`        | названия групп               |
| `directory:read_departments`   | дерево подразделений         |

Без `directory:read_users` инструмент продолжит работать: логины частично восстановятся из самого аудит-лога, но ФИО и должностей не будет.

Зависимости: `httpx`, `openpyxl`.

## Быстрый старт

```bash
# 1. Забрать историю событий (при первом запуске — максимум доступного)
python cli.py collect

# 2. Собрать отчёты
python cli.py analyze

# то же самое одной командой
python cli.py run
```

Результаты появятся в папке `result/analyze-<дата>-<время>Z/`. Симлинк `result/latest` всегда указывает на последний успешный запуск.

## Регулярный сбор

Смысл в том, чтобы не потерять события: в аудит-логах они хранятся ограниченное время, в локальной базе — постоянно.

```cron
# новые события — каждый час
0 * * * * cd /путь/к/msgaudit && ./.venv/bin/python cli.py collect >> logs/collect.log 2>&1

# отчёты и снимок состава — раз в сутки
30 7 * * * cd /путь/к/msgaudit && ./.venv/bin/python cli.py analyze --keep-runs 90 >> logs/analyze.log 2>&1
```

В cron нужен полный путь к `./.venv/bin/python` — виртуальное окружение там не активируется. Переменные окружения тоже не наследуются, задайте их в начале crontab или оберните вызов в скрипт.

## Ручная выгрузка

Панель управления организацией не позволяет выгрузить чаты в Excel, но таблицу можно сформировать вручную. Такая таблица закрывает главный пробел аудит-лога — чаты, созданные раньше доступной истории, а также чаты, в которых не было никаких событий из аудит-лога.

Ожидаемые колонки (порядок не важен, распознаются русские и английские названия):

| Колонка                         | Обязательна | Примечание                               |
|---------------------------------|-------------|------------------------------------------|
| `chat_name` / Название чата     | да          |                                          |
| `Email` / Почта / Логин         | да          | по нему ищется сотрудник                 |
| `messenger_chat.created` / Дата | нет         | трактуется как дата добавления участника |
| `chat_description` / Описание   | нет         |                                          |
| `Тип`                           | нет         | Канал, Групповой чат, Личный чат         |
| `Full name` / ФИО               | нет         | директория важнее таблицы                |
| `Job Position` / Должность      | нет         | директория важнее таблицы                |
| `Role` / Роль                   | нет         |                                          |
| `Added by` / Кем добавлен       | нет         |                                          |

Сначала проверьте таблицу без обращения к сервисам:

```bash
python cli.py validate --manual выгрузка.xlsx --manual-tz "+03:00"
```

Затем используйте в основном прогоне:

```bash
python cli.py run --manual выгрузка.xlsx --manual-tz "+03:00"
```

**Про часовой пояс.** Excel хранит даты числом и не хранит часовой пояс. Без `--manual-tz` даты считаются как UTC, и при сравнении с аудит-логом появится систематический сдвиг. Указывайте пояс, в котором формировалась выгрузка.

## Как разрешаются противоречия

Данные из разных источников не перезаписывают друг друга произвольно. Приоритеты:

| Что                                | Кто главный                 | Кто дополняет                     |
|------------------------------------|-----------------------------|-----------------------------------|
| Дата добавления, кто добавил, роль | аудит-лог                   | ручная таблица заполняет пропуски |
| ФИО, должность                     | директория сотрудников      | ручная таблица заполняет пропуски |
| Признак «это бот»                  | аудит-лог, затем директория | вид логина — только как догадка   |

Любое расхождение не исправляется молча, а попадает в `discrepancies.csv`. Например: даты добавления разошлись больше чем на сутки, ФИО в таблице и в директории разные, участник есть в таблице но отсутствует в логе.

Если в аудит-логе несколько чатов с одинаковым названием и типом, сопоставить их с таблицей автоматически нельзя — такие случаи попадают в `chat_match_issues.csv`. Разрешить вручную можно файлом соответствий:

```csv
chat_name;type;chat_key
Склад 1;group;11111111-2222-3333-4444-555555555555
```

```bash
python cli.py run --manual выгрузка.xlsx --manual-map соответствия.csv
```

| `unresolved_identities.csv` | адреса из таблицы, которых нет в директории, с подсказкой о причине  |
| `unresolved_uids.csv`       | участники, у которых известен только номер                           |
| `learned_identities.csv`    | связки «номер — логин», установленные по ручной таблице              |
| `data_quality.csv`          | замечания к заполнению таблицы                                       |
| `manual_issues.csv`         | ошибки чтения таблицы                                                |
| `run_diff.csv`              | изменения состава с прошлого запуска                                 |
| `summary.json`              | сводные числа                                                        |
| `manifest.json`             | условия запуска: время, ключи, отпечатки входных файлов              |
| `compare_with_previous/`    | сравнение с предыдущим запуском                                      |

### Как читать колонку `source` в `members.csv`

| Значение                  | Смысл                                                 |
|---------------------------|-------------------------------------------------------|
| `audit_projection`        | точно из аудит-лога                                   |
| `audit_projection+manual` | из лога, подтверждено ручной таблицей                 |
| `manual_import`           | только из ручной таблицы                              |
| `group_expansion`         | восстановлено по составу группы, дата приблизительная |

### Как читать колонку `bot_evidence`

| Значение               | Тип                                          |
|------------------------|----------------------------------------------|
| `audit_log`            | факт: флаг `is_robot` в событии              |
| `directory`            | факт: флаг `is_robot` в справочнике          |
| `manual_login_pattern` | догадка по виду логина `yndx-mssngr-...-bot` |

Догадка применяется только к ручной таблице и только для ботов, добавленных раньше доступной истории аудит-лога. Если аудит-лог говорит, что участник не бот, а логин похож на бота — доверие аудит-логу, а расхождение попадает в `discrepancies.csv`.

## История и сравнение запусков

Каждый прогон `analyze` создаёт отдельную папку и не затирает предыдущие. База данных при этом общая.

```bash
# список запусков
python cli.py runs

# сравнить последний с предыдущим
python cli.py compare

# сравнить произвольные два по номерам из списка runs
python cli.py compare --from 1 --to 5
```

Сравнение показывает появившиеся и исчезнувшие чаты, добавленных и удалённых участников, смену ролей, переименования. Если запуски делались с разными ключами, инструмент предупредит: часть различий будет вызвана сменой режима, а не реальными изменениями в чатах.

Состав чата на произвольную дату из накопленной истории:

```bash
python cli.py at --chat-key 11111111-2222-3333-4444-555555555555 \
                 --at "2026-03-01T00:00:00+00:00"
```

Идентификатор чата берётся из колонки `chat_key` файла `chats.csv`. Точность истории здесь равна частоте запусков: при ежедневном прогоне состав восстанавливается с точностью до суток. События внутри одного дня отражены в самом аудит-логе.

## Все флаги

### Ручная таблица

| Флаг                               | Значение                                                                       |
|------------------------------------|--------------------------------------------------------------------------------|
| `--manual ФАЙЛ`                    | файл `.xlsx`, `.xlsm` или `.csv` с выгрузкой                                   |
| `--manual-sheet ИМЯ`               | название листа Excel; по умолчанию первый                                      |
| `--manual-tz СМЕЩЕНИЕ`             | часовой пояс дат в таблице, например `+03:00`; по умолчанию UTC                |
| `--manual-date-semantics ЗНАЧЕНИЕ` | `member_added` (по умолчанию) — колонка с датой означает дату добавления участника; `chat_created` — дату создания чата                                                                                   |
| `--manual-map ФАЙЛ`                | файл соответствий `chat_name;type;chat_key` для чатов с одинаковыми названиями |

### Директория сотрудников

| Флаг                          | Значение            |
|-------------------------------|---------------------|
| `--directory-source ЗНАЧЕНИЕ` | `auto` (по умолчанию) — пробовать оба адреса; `cloud` — только основной; `api360` — только резервный; `none` — не обращаться к директории |
| `--allow-empty-directory`     | продолжать работу, если директория недоступна; логины и ФИО останутся пустыми. Без этого флага прогон останавливается с объяснением            |
| `--no-resolve-uids`           | не искать логины по номерам сотрудников; быстрее, но в отчёте будут только числовые номера                                                |

### Что включать в отчёт

| Флаг                    | Значение                                                               |
|-------------------------|------------------------------------------------------------------------|
| `--expand-groups`       | разворачивать группы и подразделения в конкретных людей. Даёт полный состав, но датой добавления считается момент привязки группы. Делает много запросов, работает заметно дольше        |
| `--include-private`     | включать личные переписки один на один. По умолчанию исключены         |
| `--backfill-days ЧИСЛО` | за сколько дней забрать историю при первом `collect`; по умолчанию 180 |

### Результаты

| Флаг                  | Значение                                                                     |
|-----------------------|------------------------------------------------------------------------------|
| `--results-dir ПАПКА` | папка с результатами; по умолчанию `./result`                                |
| `--run-tag МЕТКА`     | пометка в названии папки запуска, попадает в список `runs`                   |
| `--keep-runs ЧИСЛО`   | хранить только указанное число последних запусков; по умолчанию хранятся все |
| `--no-compare`        | не сравнивать автоматически с прошлым запуском                               |
| `--db ФАЙЛ`           | файл локальной базы; по умолчанию `./msgaudit.sqlite3`                       |

### Для команды `compare`

| Флаг                  | Значение                                                   |
|-----------------------|------------------------------------------------------------|
| `--from ССЫЛКА` | с чем сравнивать: `prev` (по умолчанию), `latest`, номер из списка `runs`, `-2` для предпоследнего, название папки                                                                       |
| `--to ССЫЛКА`         | что сравнивать: `latest` (по умолчанию) или те же варианты |
| `--compare-out ПАПКА` | куда положить отчёт сравнения                              |

### Для команды `at`

| Флаг                       | Значение                                                                |
|----------------------------|-------------------------------------------------------------------------|
| `--chat-key ИДЕНТИФИКАТОР` | идентификатор чата из колонки `chat_key` файла `chats.csv`              |
| `--at МОМЕНТ`              | момент времени в формате ISO 8601, например `2026-03-01T00:00:00+00:00` |

## Устройство

```
cli.py               команды и вывод
config.py            настройки
http_base.py         HTTP-клиент с повторными попытками
clients.py           обращения к аудит-логу, директории и api360
store.py             локальная база событий
projection.py        восстановление состояния чатов по событиям
resolver.py          поиск сотрудника по номеру или адресу
identity_store.py    постоянный кэш связок «номер — логин»
audit_identities.py  извлечение логинов из самого аудит-лога
manual_import.py     чтение ручной таблицы
merge.py             сведение таблицы с аудит-логом
snapshots.py         история состава чатов
report.py            выгрузка файлов отчёта
compare_runs.py      сравнение запусков
run_layout.py        папки запусков и их описания
human.py             форматирование текста для человека
doctor.py            проверка доступов
text_utils.py        нормализация строк
```

Состояние чатов восстанавливается проигрыванием событий по времени. События дедуплицируются по `idempotency_id`, поэтому повторный сбор с перекрытием окна безопасен. Позиция последнего обработанного события хранится в базе, так что каждый следующий `collect` забирает только новое.

Сведения о сотрудниках ищутся последовательно в четырёх местах: основной адрес директории, резервный адрес, сам аудит-лог (в событии рядом лежат номер сотрудника и его логин), постоянный локальный кэш. Каждый следующий источник заполняет пропуски и не портит найденное ранее. Локальный кэш помнит уволенных, которых в справочнике уже нет.

## Частые вопросы

**Ничего не нашлось, отчёты пустые.** Сначала выполните `collect` — без событий в базе восстанавливать нечего.

**Все логины пустые, вместо них числа.** Нет права `directory:read_users`. Проверьте `doctor`, посмотрите `unresolved_uids.csv`.

**Много строк в `unresolved_identities.csv`.** Смотрите колонку `hint`. Мессенджер-ботов в директории нет вообще, это нормально. Адреса на чужих доменах — участники из других организаций.

**Даты в отчёте сдвинуты на несколько часов.** Не указан `--manual-tz`. Excel не хранит часовой пояс.

**Сравнение показывает сотни изменений, хотя ничего не менялось.** Запуски делались с разными ключами, чаще всего `--expand-groups`. Инструмент об этом предупреждает в начале вывода.

**Повторный `collect` тянет всю историю заново.** Потерян или пересоздан файл базы — в нём хранится позиция последнего события.

## Безопасность данных

Инструмент работает с персональными данными сотрудников: логинами, ФИО,
должностями, составом чатов. Учитывайте это при обращении с результатами.

**Что содержит персональные данные:** все файлы в `result/`, локальная база
событий, логи запусков.

**Токены** передаются только через переменные окружения и в файлы не
записываются. В `manifest.json` сохраняются настройки запуска, но поля с
токенами оттуда вырезаются. В выводе `doctor` токен маскируется, номера
сотрудников не выводятся — сравнивается только форма записи.
