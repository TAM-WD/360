# authentik → Yandex 360 SCIM adapter

Небольшой адаптер для синхронизации пользователей из **authentik в Яндекс 360**. Преобразует обновление пользователя через `PUT` в ограниченный набор операций `PATCH`, затем проверяет сохранённые значения отдельным `GET`.

## Зачем он нужен

Адаптер устраняет несовместимость запросов PUT, заменяя его на PATCH. Поведение описано по результатам проверки на тестовом стенде.

```mermaid
flowchart LR
    AD[Active Directory] -->|LDAP / LDAPS| AK[authentik]
    AK -->|SCIM: GET, POST, PUT| BR[Адаптер]
    BR -->|HTTPS: GET, POST, PATCH| YA[Яндекс 360]
```

Адаптер не читает AD, не обрабатывает пароли сотрудников, не обслуживает SSO и не запускает синхронизацию по собственному расписанию. Выбор пользователей, преобразование атрибутов и запуск синхронизации остаются в authentik. Для входа сотрудников отдельно используется SAML/SSO.

## Что поддерживается

| Запрос от authentik | Поведение адаптера |
| --- | --- |
| `GET /v2/Users` и `GET /v2/Users/{id}` | Передаёт в Яндекс, включая query-параметры |
| `POST /v2/Users` | Передаёт создание пользователя в Яндекс после минимальной проверки JSON |
| `PUT /v2/Users/{id}` | Читает текущего пользователя, отправляет изменившиеся поля через PATCH, проверяет результат |
| `GET /v2/Groups` и `GET /v2/Groups/{id}` | Передаёт чтение в Яндекс; доступность зависит от upstream |
| `GET /v2/ServiceProviderConfig` | Возвращает консервативную конфигурацию возможностей адаптера |
| `GET /healthz` | Проверяет только работу HTTP-сервера, без обращения в Яндекс |

**Обновляемые поля:** `name.givenName`, `name.familyName`, `active`.

`active=false` используется для блокировки, `active=true` — для разблокировки. Адаптер не удаляет и не пересоздаёт пользователя. Перед записью проверяется совпадение `userName`, а также `externalId`, если он заполнен в ответе. После записи проверяются ID и запрошенные значения имени, фамилии и статуса.

При отсутствии изменений PATCH не отправляется. Пропущенные в PUT поля имени и `active` сохраняют текущие значения. Следовательно, PUT здесь имеет специально ограниченную семантику обновления, а не полную семантику замены ресурса SCIM.

Не поддерживаются адаптером:

- переименование `userName` и изменение `externalId`;
- обновление email, `displayName`, телефонов, должности, подразделения и прочих полей;
- удаление пользователей и запись групп;
- входящие PATCH, Bulk, ETag и условные записи;
- маршруты `/Schemas`, `/ResourceTypes` и универсальная совместимость с другими SCIM-клиентами.

Входящий PATCH отключён намеренно: преобразование в PATCH выполняется внутри адаптера. Поэтому в его `ServiceProviderConfig` указано `patch.supported=false`.

## Состав и требования

В составе проекта 2 файла:

```text
adapter.py    Исходный код приложения
README.md     Установка, настройка authentik и эксплуатация
```

Весь код mappings приведён ниже. Адаптер использует только стандартную библиотеку Python.

Инструкция рассчитана на Ubuntu 24.04 LTS с Python 3.12+ и systemd. Предполагается, что authentik уже установлен, пользователи доступны в нём, а в Яндекс 360 включён SCIM и получены исходный SCIM URL и токен. Для источника AD предварительно должна работать синхронизация AD → authentik.

## 1. Подготовьте Ubuntu и скопируйте файл

Все команды Bash выполняются в SSH-терминале Ubuntu. Блоки Python из раздела mappings вставляются в интерфейс authentik, а не в SSH.

Установите Python и вспомогательные утилиты:

```bash
sudo apt-get update
sudo apt-get install -y python3 ca-certificates curl nano
python3 --version
```

Скачайте репозиторий на Ubuntu или передайте туда `adapter.py`. Перейдите в каталог, **где лежит скачанный `adapter.py`**, и выполните:

```bash
ls -l adapter.py
sudo install -d -m 0755 /opt/y360-scim-adapter
sudo install -m 0644 adapter.py /opt/y360-scim-adapter/adapter.py
```

Если файл уже лежит в `/opt/y360-scim-adapter/adapter.py`, повторно копировать его не нужно.

## 2. Настройте адрес Яндекса

Создайте файл конфигурации на сервере:

```bash
sudo nano /etc/y360-scim-adapter.env
```

Вставьте одну строку, заменив `YOUR_DOMAIN_ID` идентификатором из **исходного SCIM URL вашей организации Яндекс 360**:

```dotenv
Y360_UPSTREAM=https://YOUR_DOMAIN_ID.scim-api.passport.yandex.net/v2/
```

Не подставляйте наугад ID организации из другого API. Надёжнее скопировать исходный SCIM URL целиком. В nano сохраните файл клавишами **Ctrl+O**, затем **Enter**, выйдите через **Ctrl+X**.

```bash
sudo chmod 600 /etc/y360-scim-adapter.env
```

Токен в этот файл не помещается: он будет указан в SCIM-провайдере authentik. Файл создаётся при установке и не публикуется в репозитории.

## 3. Создайте службу systemd

Создайте системного пользователя без интерактивного входа. Если он уже существует, команда не пересоздаст его:

```bash
if ! id y360-scim >/dev/null 2>&1; then
    sudo useradd --system --user-group --no-create-home --home-dir /nonexistent --shell /usr/sbin/nologin y360-scim
fi
```

Скопируйте **весь следующий блок**, от `sudo tee` до заключительного `UNIT`, в SSH и выполните:

```bash
sudo tee /etc/systemd/system/y360-scim-adapter.service >/dev/null <<'UNIT'
[Unit]
Description=authentik to Yandex 360 SCIM adapter
Wants=network-online.target
After=network-online.target

[Service]
Type=exec
User=y360-scim
Group=y360-scim
WorkingDirectory=/opt/y360-scim-adapter
EnvironmentFile=/etc/y360-scim-adapter.env
ExecStart=/usr/bin/python3 -u /opt/y360-scim-adapter/adapter.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
UNIT
```

Запустите службу и включите автозапуск:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now y360-scim-adapter.service
sudo systemctl status y360-scim-adapter.service --no-pager
```

Ожидается `active (running)`. Служба продолжит работать после закрытия SSH; при аварийном завершении systemd попытается запустить её снова. Параметры описаны в [документации systemd для Ubuntu](https://manpages.ubuntu.com/manpages/noble/man5/systemd.service.5.html).

Если запуск не удался:

```bash
sudo journalctl -u y360-scim-adapter.service -n 50 --no-pager
```

## 4. Проверьте HTTP и доступ из authentik

На Ubuntu с адаптером выполните:

```bash
curl --noproxy '*' --fail --show-error --max-time 5 http://127.0.0.1:8080/healthz
```

Ожидаемый ответ:

```json
{"status": "ok", "adapter": "y360-lab-v1"}
```

Это проверка HTTP-сервера. Она не проверяет токен и соединение с Яндексом.

Исходный код всегда слушает **`0.0.0.0:8080`**, то есть все IPv4-интерфейсы машины. Адрес и порт не настраиваются переменными окружения. Для соединения используйте реальный адрес сервера, а не `0.0.0.0`.

Выберите адрес для SCIM-провайдера:

| Где работает authentik | URL адаптера |
| --- | --- |
| На той же ОС, без контейнера и отдельного сетевого пространства | `http://127.0.0.1:8080/v2/` |
| В контейнере на той же Ubuntu | `http://ADAPTER_PRIVATE_IP:8080/v2/` — внутренний IP Ubuntu-хоста |
| На другой машине в приватной сети | `http://ADAPTER_PRIVATE_IP:8080/v2/` — внутренний IP машины с адаптером |

Замените `ADAPTER_PRIVATE_IP` своим внутренним IP. **В контейнере `127.0.0.1` относится к самому контейнеру**, а не к Ubuntu-хосту.

Обеспечьте доступ от worker authentik к TCP 8080 на машине с адаптером. В облачной группе безопасности и локальном firewall разрешайте этот порт только из нужной приватной сети/от источника authentik. На самом адаптере должны работать DNS и исходящий HTTPS к Яндексу. Входящий HTTP содержит Bearer-токен: не открывайте 8080 в интернет и не используйте недоверенную сеть.

Если authentik работает в Docker, можно проверить доступ **из его worker**. В каталоге действующего Compose-проекта authentik выполните, заменив `ADAPTER_PRIVATE_IP`:

```bash
docker compose exec -T worker python -c 'import urllib.request; o=urllib.request.build_opener(urllib.request.ProxyHandler({})); print(o.open("http://ADAPTER_PRIVATE_IP:8080/healthz", timeout=5).read().decode())'
```

Эта необязательная команда относится к уже установленному authentik; сам адаптер запускается через systemd. Если проверка на Ubuntu успешна, а из worker нет, сначала исправьте адрес, маршрутизацию или правила TCP 8080. Переключать SCIM-провайдер до появления доступа не нужно.

## 5. Подготовьте SCIM-провайдер authentik

Названия разделов приведены для authentik 2026.8.x; в других версиях расположение элементов может отличаться.

Откройте **Applications → Providers → ваш SCIM-провайдер**. Перед изменением параметров включите **Dry run** и сохраните исходный URL и выбранные mappings.

Если провайдера ещё нет, создайте SCIM-провайдер в режиме Dry run и подключите его как **backchannel provider** к нужному приложению. SAML-провайдер входа остаётся отдельным. Если провайдер уже синхронизировал пользователей, редактируйте его, сохраняя связи с удалёнными учётными записями. Удаление и пересоздание провайдера может потерять эти связи; автоматическое восстановление сопоставлений не входит в возможности адаптера.

В приложении ограничьте область синхронизации пилотной группой через **Policy / Group / User Bindings**. Проверьте фактический список пользователей в Dry run. Фильтр групп SCIM-провайдера сам по себе не является фильтром пользователей.

При проверке блокировки пользователь должен оставаться в области синхронизации. Требуется передать `is_active=false`, а не удалить объект или исключить его из группы доступа: исключение может вызвать DELETE, который адаптер отклоняет.

Для выбранных пользователей оставьте один источник записи в Яндекс. Если их изменяет YandexADSCIM или другой агент, остановите его синхронизацию на время работы через этот провайдер.

## 6. Вставьте mapping пользователя

Откройте **Customization → Property Mappings → Create** и выберите **SCIM Provider Mapping** для пользователя. Назовите его, например, `Yandex360 adapter user`.

Вставьте **всё содержимое следующего блока** в поле **Expression** и сохраните. Это выражение authentik, не самостоятельный скрипт для Ubuntu. Его код совпадает с исходным mapping стенда.

```python
user = getattr(request, "user")
email = getattr(user, "email")
attrs = getattr(user, "attributes", {})
if not email:
    raise ValueError("Yandex360 user needs email")
remote = getattr(connection, "attributes", {}) if connection else {}
result = {
    "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User"],
    "userName": email,
    "externalId": remote.get("externalId") or email,
    "name": {
        "givenName": attrs.get("givenName", ""),
        "familyName": attrs.get("sn", ""),
    },
    "active": getattr(user, "is_active"),
}
if not connection:
    result["emails"] = [{"value": email, "type": "work", "primary": True}]
return result
```

Выражение использует:

- `user.email` для `userName`;
- атрибуты `givenName` и `sn` для имени и фамилии;
- `user.is_active` для блокировки и разблокировки;
- существующий непустой `externalId`, а при его отсутствии — email.

Поле `emails` включается только при создании пользователя. При обновлении оно не отправляется, поскольку адаптер не поддерживает его изменение.

Убедитесь, что LDAP mapping действительно заполняет `givenName`, `sn`, email и правильно передаёт состояние активности из AD. Отсутствующие имя/фамилия превращаются в пустые строки и могут очистить эти поля в Яндексе. Сам адаптер не читает `userAccountControl` из AD.

В SCIM-провайдере выберите **только этот пользовательский mapping** вместо стандартных: дополнительные mappings могут добавить неподдерживаемые поля, и PUT будет отклонён с кодом 400.

## 7. Вставьте mapping исключения групп

В том же разделе создайте **SCIM Provider Group Mapping** с именем, например, `Yandex360 adapter skip groups`.

В поле **Expression** вставьте:

```python
raise SkipObject
```

`SkipObject` предоставляется средой выражений authentik. Выберите **только этот mapping** в групповых mappings SCIM-провайдера. Пустой список mappings не следует считать гарантией отключения синхронизации групп.

## 8. Переключите URL и проверьте синхронизацию

Заполните SCIM-провайдер:

| Поле | Значение |
| --- | --- |
| URL | Адрес из шага 4 с окончанием `/v2/` |
| Authentication mode | Bearer token / Token |
| Token | Действующий SCIM-токен Яндекс 360 |
| User mappings | Только `Yandex360 adapter user` |
| Group mappings | Только `Yandex360 adapter skip groups` |
| Dry run | Включён на этапе настройки |

Сохранение настроек может поставить задачу синхронизации в очередь. Пока Dry run включён, проверьте область действия, сопоставление пользователей и план изменений. Dry run не доказывает успешность записи в Яндекс.

После проверки отключите Dry run и дождитесь штатной синхронизации. Адаптер не имеет своего таймера, не меняет расписания LDAP/SCIM и не требует принудительного запуска. Время доставки зависит сначала от импорта AD → authentik, затем от событий и расписаний SCIM самого authentik.

Для новой установки проверьте на пилотных учётках:

1. Создание пользователя.
2. Изменение имени/фамилии существующего пользователя.
3. Передачу `active=false`.
4. Передачу `active=true`.

Проверяйте результат в Яндексе и сохранение прежнего ID при изменениях. Запись `translated_update` со статусом 200 — это ответ на PATCH. Окончательный успех обновления требует последующего GET и итогового ответа адаптера 200.

SSO работает независимо от этого маршрута. Его настройки для подключения SCIM-адаптера менять не требуется.

## Как обрабатывается обновление


1. Проверяются разрешённые поля, типы и ID в URL/теле.
2. Выполняется `GET /Users/{id}` с токеном отправителя.
3. Проверяется совпадение `userName`. Если у текущего пользователя в Яндексе заполнен `externalId`, проверяется и его совпадение.
4. Для отличающихся полей формируется SCIM `PatchOp` с операциями `replace`.
5. Выполняется один PATCH. Запись автоматически не повторяется.
6. После PATCH 200/204 выполняется до трёх GET, с паузами 1 и 2 секунды между повторными чтениями.
7. При совпадении ID и запрошенных значений имени, фамилии и `active` возвращается полный User и статус 200. Если подтверждения нет — 502. Повторного сравнения `userName` и `externalId` после PATCH в исходной версии нет.

502 после записи не означает откат: изменение могло уже сохраниться. Перед ручной повторной записью проверьте фактическое состояние. Возобновление штатных задач и повторные попытки определяет authentik.

Исходная версия не сериализует обновления одного ID: параллельные последовательности GET → PATCH → GET могут пересекаться. Используйте один экземпляр адаптера и один источник записи для выбранных пользователей; это ограничивает число источников конфликтов, но не добавляет блокировок внутри процесса.

## Управление службой

```bash
sudo systemctl status y360-scim-adapter.service --no-pager
sudo journalctl -u y360-scim-adapter.service -n 100 --no-pager
sudo journalctl -u y360-scim-adapter.service -f
```

Последняя команда показывает новые записи в реальном времени. **Ctrl+C** завершает просмотр журнала, а не службу.

```bash
sudo systemctl restart y360-scim-adapter.service
sudo systemctl stop y360-scim-adapter.service
sudo systemctl start y360-scim-adapter.service
```

После изменения `/etc/y360-scim-adapter.env` или замены `adapter.py` перезапустите службу. После изменения самого unit-файла сначала выполните `sudo systemctl daemon-reload`, затем перезапуск. Остановка адаптера прерывает доставку SCIM через него, но не откатывает изменения в Яндексе.

Сам Python-файл не читает `.env` автоматически. При запуске службой переменную `Y360_UPSTREAM` загружает systemd через `EnvironmentFile`.

### Ручной запуск для диагностики

Этот способ временно заменяет запуск службой. Не запускайте два экземпляра на одном порту. Остановите именно службу адаптера, затем укажите свой исходный SCIM URL:

```bash
sudo systemctl stop y360-scim-adapter.service
export Y360_UPSTREAM='https://YOUR_DOMAIN_ID.scim-api.passport.yandex.net/v2/'
python3 -u /opt/y360-scim-adapter/adapter.py
```

Приложение останется в терминале. После диагностики нажмите **Ctrl+C** и верните службу:

```bash
sudo systemctl start y360-scim-adapter.service
```

## Типичные ошибки

| Ошибка | Что проверить |
| --- | --- |
| `KeyError: 'Y360_UPSTREAM'` | Переменная не передана процессу: проверьте EnvironmentFile и файл настроек, затем перезапустите службу |
| `Expected the existing HTTPS Yandex SCIM /v2 origin` | В URL остался placeholder, лишние параметры или указан неподдерживаемый адрес |
| `Address already in use` | Порт 8080 занят: `sudo ss -ltnp 'sport = :8080'`. Не запускайте второй экземпляр поверх действующего |
| `Connection refused` из authentik | Служба не слушает, указан неверный адрес либо firewall отклоняет соединение; проверьте `/healthz` на сервере и из worker |
| Таймаут из authentik | Проверьте приватный IP, маршрут и правила TCP 8080 |
| `401` / `403` | Проверьте токен и его права в Яндексе; локальный `/healthz` токен не проверяет |
| `400` при PUT | Проверьте пользовательский mapping: неподдерживаемые поля, например `displayName` или `emails`, должны отсутствовать при обновлении |
| `409` | Запрос пытается изменить `userName` или непустой `externalId` существующего пользователя |
| `405` | Клиент пытается удалить пользователя, записать группу или отправить входящий PATCH |
| `502` | Ошибка upstream, слишком большой ответ либо GET не подтвердил результат PATCH; прочитайте detail ответа и проверьте состояние в Яндексе |

## Ограничения адаптера

- Поддерживается только один фиксированный upstream. Код допускает HTTPS, хост с суффиксом `.scim-api.passport.yandex.net`, метку из латинских букв, цифр и дефиса, путь `/v2` и стандартный порт 443. Параметры, фрагменты и учётные данные в URL запрещены.
- Bearer-токен берётся из входящего запроса. Адаптер не сохраняет его; действительность токена для перенаправляемых операций проверяет Яндекс. Локальный `ServiceProviderConfig` не проверяет токен в Яндексе.
- Проверка TLS при соединении с Яндексом включена, HTTP-перенаправления запрещены. Системные HTTP proxy-переменные игнорируются.
- Входящий HTTP не шифруется; сервис предназначен для доверенной приватной сети. В коде нет встроенного TLS.
- Сервер использует стандартный `http.server`, который [документация Python не рекомендует для production](https://docs.python.org/3/library/http.server.html). systemd обеспечивает управление процессом, но не меняет ограничений HTTP-сервера.
- Нет собственной базы, очереди, распределённых блокировок и ограничения частоты запросов. Параллельные обновления одного пользователя могут пересекаться.
- Лимит тела запроса и ответа upstream — 1 МиБ. Для больших каталогов уменьшайте размер страницы SCIM-клиента.
- Таймаут транспорта — 20 секунд на операцию, а не на всю последовательность GET → PATCH → GET.
- Статус и тело ответа upstream передаются, но заголовки, включая Retry-After и ETag, не сохраняются.
- Входящий chunked transfer не поддерживается.
- Логи содержат метод, статус, путь без query-параметров и названия изменяемых полей. Путь может содержать пользовательский ID. Токены и тела запросов намеренно не логируются.
